Git: cherry-pick, stash, rebase и bisect — простыми словами

Четыре команды, которые отличают уверенного разработчика: зачем они нужны, когда применять и чем опасны. На аналогиях, с командами и ответами для интервью.

1 Четыре команды — четыре разные задачи

Git хранит всю историю проекта: кто, что и когда менял. Но иногда историю нужно подправить: перенести один фикс в другую ветку, временно убрать недоделанное, привести свои коммиты в порядок или найти тот самый коммит, после которого всё сломалось. Для этого есть четыре инструмента.

КомандаЗадачаАналогия
cherry-pick Перенести один конкретный коммит в другую ветку Скопировать один рецепт из чужой книги в свой блокнот
stash Временно убрать незакоммиченные изменения Сложить недоделанное в ящик стола и достать позже
rebase -i Переписать свою историю: склеить, переставить, переименовать коммиты Привести черновик в порядок перед сдачей
bisect Найти коммит, который сломал работу Найти перегоревшую лампочку в гирлянде делением пополам
Главное отличие. cherry-pick и rebase создают новые коммиты с новыми SHA. stash просто прячет изменения, а bisect вообще ничего не меняет — только переключает коммиты и спрашивает «здесь ещё работает?».

2 cherry-pick: перенести один коммит

Идея на пальцах В одной ветке есть коммит с нужным исправлением. Мы берём только его и применяем в другой ветке. Вся остальная история первой ветки нам не нужна.

Представь, что у тебя две книги рецептов. В одной появился хороший рецепт супа. Ты не забираешь всю книгу — просто переписываешь один рецепт в свою. В Git это и есть cherry-pick: изменения скопированы, но связи с исходным коммитом нет.

Когда нужно

  • Хотфикс сделали в main, а он нужен ещё в release/1.4 и release/1.3.
  • Нужен один коммит из чужой ветки, а вся ветка ещё сырая.
  • Случайно закоммитили не в ту ветку — переносим коммит куда надо.
main · фикс готов → release/1.4 · копия фикса

Новый коммит, новый SHA, тот же набор изменений.

Команды

git switch release/1.4
git cherry-pick -x 4f2c9ab

# если конфликт: правим файлы, затем
git add .
git cherry-pick --continue

# или отменить перенос целиком
git cherry-pick --abort

Флаг -x дописывает в сообщение коммита строку вида «cherry picked from commit 4f2c9ab». Через полгода это объяснит, откуда взялся фикс.

Cherry-pick не заменяет merge. Он копирует изменения, а не историю. Если потом влить исходную ветку целиком, те же изменения могут прийти второй раз — получится конфликт или дубль. Для «забрать всю ветку» нужен merge, для «забрать один фикс» — cherry-pick.

3 stash: убрать недоделанное на время

Идея на пальцах Ты правишь код, но срочно нужно переключиться на другую задачу. Коммитить сырое не хочется. Тогда изменения складываются в ящик стола — рабочая папка становится чистой, можно спокойно переключаться. Потом ящик открывается, и работа возвращается.

Когда нужно

  • Срочный баг в другой ветке, а текущая правка ещё не готова.
  • Нужно подтянуть свежий main, но есть незакоммиченные файлы.
  • Хочется проверить чужую ветку, не теряя свою работу.

Команды

# убрать изменения, включая новые файлы (-u)
git stash push -u -m "wip: player retry"

git stash list
git stash show -p stash@{0}

# переключились, сделали дела, вернулись
git stash pop      # применить и удалить из стека
git stash apply    # применить и оставить в стеке
КомандаЧто делает
git stash push -uПрячет изменения вместе с новыми (untracked) файлами
git stash listПоказывает все сохранённые записи
git stash show -pПоказывает, что лежит в записи
git stash popДостаёт и удаляет запись, если конфликтов нет
git stash applyДостаёт, но запись оставляет
git stash dropУдаляет запись, не применяя
Stash — не бэкап. Это временное хранилище, и оно легко превращается в свалку из десяти забытых записей. Если работа важная — лучше сделать коммит в отдельной ветке. И помни: без -u новые файлы останутся в рабочей папке и переедут вместе с тобой в другую ветку.

4 rebase -i: привести свою историю в порядок

Идея на пальцах У тебя есть черновик: три коммита «правка», «ещё правка», «ой, забыл файл». Перед сдачей их хочется склеить в один понятный коммит и переписать сообщение. Interactive rebase — это редактор твоей истории: переставить коммиты, склеить, переименовать или выбросить.

Обычный rebase переносит твои коммиты на свежую основную ветку. Флаг -i (interactive) открывает список коммитов и даёт выбрать, что с каждым сделать.

ДействиеЧто произойдёт
pickОставить коммит как есть
rewordОставить изменения, переписать сообщение
squashСклеить с предыдущим, объединив сообщения
fixupСклеить с предыдущим, выбросив своё сообщение
editОстановиться и дать поправить коммит
dropВыбросить коммит

Команды

git switch feature/player
git fetch origin
git rebase origin/main

# конфликт: правим файлы, затем
git add .
git rebase --continue
# или отменить всё
git rebase --abort

# привести в порядок последние три коммита
git rebase -i HEAD~3

# после переписывания СВОЕЙ ветки
git push --force-with-lease
Золотое правило rebase. Переписывать можно только свою, ещё не опубликованную историю. Если ветку уже забрали коллеги, rebase поменяет SHA, и у всех разъедется история. Общие ветки — main, release, develop — не rebase'ят.

Чем --force-with-lease лучше --force: он push'ит только если удалённая ветка не менялась с твоего последнего fetch. Если кто-то успел запушить, Git откажется, и чужая работа не пропадёт.

5 bisect: найти коммит, который всё сломал

Идея на пальцах В гирлянде перегорела одна лампочка. Можно проверять по одной — долго. А можно делить гирлянду пополам: если половина не горит, проблема там, вторую половину можно не трогать. git bisect делает то же самое с коммитами.

Ты знаешь, что на версии v1.42.0 всё работало, а сейчас — нет. Между ними, скажем, 1000 коммитов. Bisect включает середину, ты проверяешь и говоришь «работает» или «сломано». Каждая проверка отбрасывает половину оставшихся. 1000 → 500 → 250 → … Примерно 10 проверок, потому что 210 ≈ 1024.

Ручной режим

git bisect start
git bisect bad              # текущий коммит сломан
git bisect good v1.42.0     # последний известный рабочий

# Git переключил на середину — проверяем и говорим:
git bisect good             # здесь работает
# или
git bisect bad              # здесь уже сломано

# когда виновник найден
git bisect reset

Автоматический режим

Если есть тест, который воспроизводит баг, bisect сам прогонит его на каждом шаге:

git bisect start HEAD v1.42.0
git bisect run ./vendor/bin/phpunit --filter=PlaybackTest
Как Git понимает результат. Код возврата 0 — коммит хороший, 1–127 — плохой, 125 — «пропустить, проверить нельзя». Тест должен быть быстрым и одинаково воспроизводимым, иначе bisect покажет случайный коммит.

6 Правила и частые ошибки

Шесть правил, которые спасают

  1. Переписывай только своё. Rebase и cherry-pick меняют SHA. Общие ветки не трогаем.
  2. Перед rebase — чистое дерево. Либо закоммить, либо stash.
  3. После rebase — --force-with-lease. Никогда не --force в общую ветку.
  4. Cherry-pick — точечно. Для целой ветки есть merge.
  5. Stash — на минуты, не на недели. Важное — в коммит.
  6. Bisect — только с воспроизводимым тестом. Иначе это гадание.

Частые ошибки

  • Сделали rebase общей ветки и запушили с --force — у коллег разъехалась история.
  • Перенесли фикс через cherry-pick, а потом влили ветку целиком — двойные изменения и конфликты.
  • Забыли -u в stash: новые файлы остались и переехали в другую ветку.
  • Сделали stash pop поверх таких же изменений — конфликт и потеря времени.
  • Запустили bisect run с «плавающим» тестом — виновник найден неверно.
  • Испугались после неудачного rebase и удалили ветку. А надо было просто посмотреть git reflog.
Страховка — git reflog. Он хранит перемещения HEAD примерно 90 дней, включая состояние до rebase. Нашёл нужную запись — вернулся: git reset --hard HEAD@{2}.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Чем cherry-pick отличается от merge?

«Cherry-pick берёт изменения одного коммита и создаёт в текущей ветке новый коммит с новым SHA. Merge вливает всю ветку и сохраняет связь между ветками. Cherry-pick нужен для точечного переноса — например, хотфикса в release. Заменой merge он не является: при последующем слиянии те же изменения могут прийти второй раз и дать конфликт».

Своими словами

Это как скопировать один рецепт из чужой книги: у меня он появился, но связи с книгой нет. Merge — влить всю книгу целиком. Поэтому cherry-pick — для одного фикса, а не вместо слияния.

02Когда rebase, а когда merge?

«Rebase переписывает мои коммиты поверх свежей основной ветки и даёт линейную историю. Его применяют к личной ветке перед MR. Merge сохраняет реальную историю ветвления и безопасен для общих веток. Правило: не rebase'ить то, что уже ушло в общую ветку, иначе у коллег разъедется история».

Своими словами

Свою ветку перед MR можно почистить rebase'ом. Общую — только merge. Если перепишу общую, коллегам придётся разбираться с разъехавшейся историей.

03Зачем stash и чем pop отличается от apply?

«Stash убирает незакоммиченные изменения в стек и возвращает рабочее дерево в чистое состояние. Pop применяет изменения и удаляет запись из стека, apply — применяет и оставляет. Если при pop случился конфликт, запись остаётся».

Своими словами

Срочно надо переключиться — убрал недоделанное в ящик, потом достал. Pop — достал и выкинул ярлык, apply — достал, ярлык оставил.

04Как найти коммит, который сломал прод?

«Через git bisect. Отмечаю текущий коммит как bad, последний рабочий как good, Git делит диапазон пополам и предлагает проверить середину. Каждая проверка отбрасывает половину. Для 1000 коммитов это около 10 шагов. Проверку можно автоматизировать: git bisect run с тестом».

Своими словами

Делю историю пополам: если середина плохая — ищу в левой половине, если хорошая — в правой. Или просто отдаю тест команде bisect run, и он сам бегает.

05Зачем --force-with-lease?

«После rebase SHA меняются, и обычный push отклоняется. Force перезаписывает удалённую ветку вслепую, force-with-lease — только если удалённая ветка не изменилась с моего последнего fetch. Если кто-то успел запушить, операция отклонится, и я не потеряю его коммиты».

Своими словами

Это force с проверкой: если кто-то успел запушить, Git меня остановит, а не сотрёт чужую работу.

06Что делать, если после rebase всё сломалось?

«git reflog хранит перемещения HEAD, включая состояние до rebase. Нахожу нужную запись и делаю git reset --hard HEAD@{n} или создаю ветку от неё. Reflog хранится около 90 дней, поэтому локальные переписанные коммиты ещё доступны».

Своими словами

Смотрю reflog — там видно, где я был до rebase. Возвращаюсь на эту запись, и всё на месте.

Ответь вслух, не подглядывая. 0 / 5

Если запомнить только одно: переписывать историю можно только у себя и только до публикации. Всё, что уже ушло в общую ветку, меняется через merge.
