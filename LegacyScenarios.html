Legacy и сложные сценарии — простыми словами

Что делать с кодом, который страшно менять: как его исследовать, застраховать тестами, найти швы и заменить по частям. Плюс конкурентность, ретраи и частичные сбои — то, на чём сложные системы ломаются чаще всего.

1 Что такое legacy на самом деле

Legacy — это не «старый код». Это код, который приносит пользу и который страшно менять: нет тестов, никто не помнит, почему сделано именно так, а любая правка грозит инцидентом. Код может быть написан вчера и уже быть legacy, если его никто не понимает.

Аналогия Старый дом с несущими стенами. В нём тепло и есть жильцы, но перепланировку нельзя начать с фразы «снесём всё». Сначала чертёж, потом временные опоры, потом замена по комнатам — с людьми внутри.

На Senior-интервью проверяют не готовность «переписать всё красиво», а управляемость: умеешь ли ты исследовать систему, снижать риск, двигаться маленькими шагами и оставлять возможность отката. Ответ «выкинем и напишем заново» звучит смело, но обычно означает полгода без поставок и два набора багов.

Главная мысль. Legacy лечат не героическим переписыванием, а снижением стоимости изменения: тесты, наблюдаемость, швы и постепенная замена. Переписывание — крайний случай, а не первый шаг.

2 Как оценить legacy, прежде чем что-то трогать

Первое действие — не рефакторинг, а исследование. Нужно понять, из чего система состоит, что в ней критично и где сосредоточен риск. Без карты любая правка — это ходьба по минному полю.

Пять шагов

  1. Инвентаризация. Какие сервисы, базы, очереди и внешние API участвуют. Где точки входа: HTTP, cron, консьюмеры, CLI.
  2. Карта рисков. Где деньги, персональные данные, регуляторные требования. Эти участки трогаем последними и с максимальной страховкой.
  3. Наблюдаемость. Логи, метрики, трейсы. Если их нет, сначала добавляем: без данных о поведении нельзя понять, что сломалось после правки.
  4. Тесты-характеристики. Фиксируем текущее поведение ключевых сценариев, даже если оно странное.
  5. Метрики процесса. Как часто меняем, сколько инцидентов, сколько времени от коммита до продакшена. Это покажет, стало ли лучше.
СимптомЧто делать сначала
Любая правка ломает что-то неожиданноеCharacterization-тесты на ключевые сценарии
Непонятно, кто кого вызываетКарта зависимостей и трассировка
Инциденты разбирают по памятиЛоги с correlation id и runbook
Релиз раз в месяц и со страхомМелкие изменения, feature toggles, автоматический деплой
Все знания у одного человекаПарное программирование, ADR, документация решений
Не начинай с большого рефакторинга. Сначала выясни, что именно болит. Может оказаться, что 80% проблем создаёт один медленный запрос и отсутствие индекса, а не архитектура.

3 Characterization-тесты: страховка на время ремонта

Characterization-тест фиксирует текущее поведение кода, а не «правильное». Он отвечает на вопрос «что система делает сейчас», чтобы после рефакторинга поведение не изменилось незаметно. Если код возвращает странный формат — тест закрепляет странный формат.

Аналогия Перед ремонтом фотографируем комнату. Фотография не говорит, красиво ли расставлена мебель; она позволяет проверить, что после ремонта ничего не пропало.

Как это делается

  1. Выбрать сценарий, который приносит деньги или часто ломается.
  2. Подготовить реальные входные данные, включая неудобные: пустые поля, граничные значения, странные кодировки.
  3. Записать фактический результат — не придуманный, а полученный от текущего кода.
  4. Зафиксировать его в тесте: assert по полям или сравнение с golden-файлом.
  5. Менять код маленькими шагами. Тест должен оставаться зелёным. Если покраснел — поведение изменилось, разбираемся.
final class LegacyInvoiceCalculatorTest extends TestCase
{
    public function test_current_behavior_is_preserved(): void
    {
        $calculator = new LegacyInvoiceCalculator();

        // Входные данные взяты из реального инцидента
        $result = $calculator->calculate(
            amount: 1490,
            discount: 15,
            isVatIncluded: false
        );

        // Фиксируем то, что код возвращает СЕЙЧАС,
        // даже если формула кажется странной
        self::assertSame(1266.5, $result['total']);
        self::assertSame(211.08, $result['vat']);
    }
}

Для больших ответов удобен golden master: результат сохраняется в файл, тест сравнивает новый вывод с эталоном. Так можно покрыть целый отчёт или JSON-ответ, не описывая каждое поле вручную.

Тест не делает код правильным. Он только защищает от незаметного изменения. Если в коде известный баг, который решили сохранить, это фиксируют в комментарии к тесту и в задаче. Иначе через месяц кто-то «починит» его и сломает совместимость.

4 Швы: точки, где можно вмешаться

Seam (шов) — место в коде, где поведение можно изменить, не переписывая всё вокруг. Это точка контроля: подставить другую реализацию, перехватить вызов, включить новый путь. Без швов любой тест требует поднять весь мир.

Как сделать шов

  1. Найти прямую зависимость. `new RedisClient()`, `file_get_contents()`, статический вызов, глобальная функция.
  2. Обернуть её в свой интерфейс. Например, `Cache` с методами `get/set` вместо прямого клиента.
  3. Передавать реализацию снаружи. Через конструктор или фабрику — тогда в тесте подставляется fake, в проде — настоящая.
  4. Не менять поведение на этом шаге. Шов — это подготовка, а не новая функциональность.
// Было: жёсткая связь с файловой системой
final class ReportBuilder
{
    public function build(): string
    {
        return file_get_contents('/var/data/report.json');
    }
}

// Стало: шов через интерфейс
interface ReportSource
{
    public function read(): string;
}

final class FileReportSource implements ReportSource
{
    public function read(): string
    {
        return file_get_contents('/var/data/report.json');
    }
}

final class ReportBuilder
{
    public function __construct(private ReportSource $source) {}

    public function build(): string
    {
        return $this->source->read();
    }
}

Теперь тест передаёт `InMemoryReportSource` с нужной строкой, а прод — файл. Поведение не изменилось, но появилась точка, где можно безопасно проверять и постепенно заменять логику.

Шов не улучшает код сам по себе. Он делает изменение возможным. Польза появляется, когда через шов мы подключаем тест, новую реализацию или feature toggle.

5 Strangler Fig: замена по частям

Strangler Fig — стратегия, при которой новая реализация постепенно вытесняет старую. Название от растения, которое растёт вокруг дерева и со временем занимает его место. Старое продолжает работать, пока новое не доказало надёжность.

Клиенты→ router / proxy→ старый сервис⇄ новый сервис

Router решает, куда отправить запрос: в старый путь, новый или в оба для сравнения. Долю трафика можно менять feature toggle.

Порядок замены

  1. Поставить прокси или роутер перед старым сервисом. С этого момента точка входа одна.
  2. Выбрать один сценарий, а не весь сервис. Например, только «получить список видео».
  3. Реализовать новый путь и включить его для малой доли трафика.
  4. Сравнить результаты на одинаковых запросах: shadow traffic или логирование расхождений.
  5. Синхронизировать данные. Dual write, CDC или batch-перенос — зависит от нагрузки и требований к свежести.
  6. Увеличивать долю и держать быстрый откат флагом.
  7. Удалить старый путь и его код. Иначе legacy останется жить рядом и требовать поддержки.
Способ миграции данныхПлюсМинус
Dual writeДанные сразу в двух местахНужна обработка рассинхрона и отката
CDCНе меняет код записиСложнее настроить и сопровождать
BatchПросто и предсказуемоДанные отстают, нужен период догонки
Shadow readsПроверка без влияния на ответДвойная нагрузка на чтение
Ключевое свойство. На каждом шаге система остаётся рабочей, а откат — это переключение флага, а не восстановление из бэкапа. Именно поэтому стратегия безопаснее «большого взрыва».

6 Сложные сценарии: где ломается на самом деле

«Сложные сценарии» — это не хитрые алгоритмы, а условия реального мира: два запроса одновременно, сеть моргнула, консьюмер упал после записи в базу, ретрай пришёл дважды. Именно здесь появляются двойные списания и потерянные события.

СценарийЧто может пойти не такПриём
Повторный запросДвойное списание или дубль записиIdempotency key, unique constraint
Конкурентная правкаПоследний перезаписал первогоОптимистичная блокировка, версия строки
Запись + событиеВ БД записали, в Kafka не отправилиTransactional outbox
Частичный сбойОдин сервис ответил, другой нетSaga, компенсации, таймауты
Долгая операцияТранзакция держит блокировкиАсинхронность, короткие транзакции
ПерегрузкаРетраи усиливают нагрузкуBackoff с jitter, circuit breaker, лимиты

Как это проверять

  • Integration-тесты с реальными зависимостями. Мок не покажет, что транзакция не откатилась или событие не сериализовалось.
  • Fault injection. Намеренно роняем зависимость, обрываем соединение, добавляем задержку и смотрим, как система восстанавливается.
  • Повторная доставка. Отправляем одно и то же сообщение дважды: результат должен быть тем же.
  • Конкурентный тест. Два параллельных запроса на один ресурс: проверяем, что нет двойной записи и потерянного обновления.
  • Chaos-эксперименты на staging: отключаем pod, брокер, DNS — смотрим, срабатывают ли таймауты и деградация.
«Exactly once» — маркетинг. В распределённой системе реально достижимы at-least-once и идемпотентная обработка. Строить логику на предположении «сообщение придёт ровно один раз» — значит ждать двойного списания.

7 Правила и частые ошибки

Что работает

  • Маленькие шаги. Один сценарий за релиз, а не «новая архитектура целиком».
  • Сначала тесты и наблюдаемость, потом изменение поведения.
  • Старое и новое работают параллельно, пока новое не доказало надёжность.
  • Откат — переключатель, а не восстановление базы.
  • Бюджет на долг: постоянная доля времени, а не разовая кампания.
  • ADR на решения: почему заменили, что отбросили, чем заплатили.
  • Метрики до и после: latency, ошибки, инциденты, lead time.

Что не работает

  • Big bang rewrite. Полгода без поставок, два набора багов, потеря знаний.
  • Рефакторинг без тестов. Через неделю никто не знает, что сломалось и когда.
  • Смешивание фичи и рефакторинга в одном MR: ревьюер не может отличить изменение поведения от перестановки кода.
  • «Починим потом» без задачи, владельца и срока — это не план, а обещание.
  • Оптимизация без профиля. Переписывают красиво, а тормозит по-прежнему один SQL.
Ответ для интервью. «Legacy — это риск изменения, а не возраст. Сначала карта зависимостей и characterization-тесты, потом швы и Strangler Fig: один сценарий, роутер, доля трафика, откат флагом. Переписывание целиком — крайний вариант, когда поэтапная замена дороже».

8 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Что такое legacy и почему «переписать с нуля» — плохой первый шаг?

«Legacy — это код, который приносит пользу, но изменение которого рискованно: нет тестов, потерян контекст, высока цена ошибки. Переписывание целиком останавливает поставки, дублирует неявные требования и часто воспроизводит те же баги. Сначала я снижаю риск: карта зависимостей, наблюдаемость, characterization-тесты, затем постепенная замена по сценариям».

Своими словами

Это не «старый код», а «код, который страшно трогать». Сносить дом с жильцами нельзя; сначала укрепляем стены и меняем по комнатам.

02Что такое characterization-тест и зачем он, если фиксирует баги?

«Он фиксирует текущее поведение, а не правильное. Смысл — страховка: после рефакторинга поведение не должно измениться незаметно. Если в коде есть известный баг, который решили сохранить для совместимости, это отмечают в тесте. Тест не делает код правильным, он защищает от случайного изменения».

Своими словами

Это фотография комнаты перед ремонтом: не оценка красоты, а проверка, что ничего не пропало.

03Что такое seam и как его сделать?

«Seam — место, где можно изменить поведение без переписывания всего окружения. Практически: найти прямую зависимость вроде `new Client` или глобальной функции, обернуть её в свой интерфейс и передавать реализацию снаружи. Тогда в тесте подставляется fake, а в проде — настоящий клиент. Шов сам по себе поведение не меняет».

Своими словами

Это дверь в стене: пока её нет, в комнату можно попасть только через весь дом. Дверь не меняет комнату, но делает вход управляемым.

04Как работает Strangler Fig?

«Перед старым сервисом ставится роутер, затем один сценарий реализуется заново и включается для малой доли трафика. Результаты сравниваются, данные синхронизируются, доля растёт, откат делается флагом. Когда новый путь доказал надёжность, старый удаляется. Система всё время остаётся рабочей».

Своими словами

Новое растение растёт вокруг старого дерева, пока не займёт его место. Ни в какой момент сад не остаётся без тени.

05Какие сложные сценарии надо тестировать и как?

«Повторную доставку, конкурентную правку, частичный сбой, запись в БД без отправки события, перегрузку и ретраи. Проверяю integration-тестами с реальными зависимостями, повторной отправкой сообщений, конкурентными запросами и fault injection. Для распределённых операций использую идемпотентность, outbox, saga и таймауты, а не рассчитываю на exactly-once».

Своими словами

Сложность не в алгоритме, а в реальности: сеть моргнула, запрос повторился, два человека нажали одновременно. Это и надо ловить.

06Как убедить бизнес выделять время на техдолг?

«Перевожу долг в риск и деньги: сколько инцидентов, сколько часов поддержки, какая скорость новых фич, что будет при отказе. Предлагаю маленький постоянный бюджет, например 20% времени, и показываю эффект в метриках — lead time, change failure rate, число инцидентов. Это разговор не про красоту кода, а про предсказуемость поставок».

Своими словами

Бизнесу не интересен «чистый код», ему интересно, почему релизы страшные и почему фича делается месяц. Долг объясняют через это.
