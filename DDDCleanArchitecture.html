DDD и Clean Architecture — простыми словами

Как разложить сложный домен на понятные части, где провести границы контекстов и зачем бизнес-логику отделяют от фреймворка и базы. С примерами для видео-платформы и без культа «слоёв ради слоёв».

1 Зачем это нужно

DDD (Domain-Driven Design) — способ проектировать систему вокруг предметной области и её языка, а не вокруг таблиц базы или фреймворка. Clean Architecture — способ расположить код так, чтобы бизнес-правила не зависели от Laravel, Postgres и Kafka и их можно было тестировать отдельно.

Аналогия DDD — это чертёж здания по назначению комнат: кухня, спальня, санузел. Clean Architecture — несущие стены и коммуникации, которые не переделывают при каждой смене мебели. Вместе они дают план, который переживает ремонт.

На Senior-интервью не требуют знать все паттерны Эванса. Проверяют понимание: где проходят границы, какие термины общие с бизнесом, что является агрегатом и как изолировать домен от инфраструктуры. И обязательно — когда DDD не нужен.

DDD — не серебряная пуля. Для CRUD-сервиса из трёх таблиц полноценный DDD добавит слоёв и мапперов без пользы. Он окупается там, где правил много, они меняются и цена ошибки высока: биллинг, права, каталог, воспроизведение.

2 Домен, подобласти и ограниченные контексты

Домен — вся область бизнеса: видео-платформа. Подобласти — её крупные куски: каталог, воспроизведение, транскодинг, биллинг, рекомендации. Bounded context — явная граница, внутри которой слово имеет одно значение и действует одна модель.

Почему одно слово — разные вещи

Слово «видео» в каталоге — это карточка с названием, обложкой и жанром. В транскодинге — исходный файл, профили и очереди. В биллинге — единица тарификации. Если свести всё в один класс `Video`, получится объект на двести полей, который никто не понимает. Контексты разделяют эти значения.

Catalog→ Playback→ Transcoding→ Billing

Один и тот же фильм проходит через контексты, но в каждом у него своя модель и свои правила.

Ubiquitous language

Единый язык — термины бизнеса совпадают с именами в коде и в разговоре. Если менеджер говорит «подписка», а в коде это `user_plan_link`, мост теряется. Внутри контекста заводят словарь: «подписка», «план», «период», «продление» — и используют эти слова везде.

Практическое правило. Границу контекста часто видно по тому, где меняются слова и правила. Если две команды спорят о значении термина — возможно, это два контекста, а не один.

Value Object: деньги — не число

Сумма без валюты — источник багов. Деньги, период, разрешение видео — это значения, которые нельзя «просто сложить». Делаем неизменяемый объект с проверками в конструкторе.

final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {
        if ($amount < 0) {
            throw new InvalidArgumentException('amount must be positive');
        }
    }

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new DomainException('currency mismatch');
        }

        return new self($this->amount + $other->amount, $this->currency);
    }
}

Агрегат: одна транзакция — один агрегат

Агрегат защищает инварианты. Например, нельзя продлить отменённую подписку. Все изменения идут через корень, а сохраняется агрегат целиком. Если правило затрагивает два агрегата, это уже не одна транзакция, а событие и согласованность в процессе.

final class Subscription
{
    private SubscriptionStatus $status = SubscriptionStatus::Active;

    public function __construct(
        private SubscriptionId $id,
        private UserId $userId,
        private Period $period,
    ) {}

    public function renew(Period $next): void
    {
        if ($this->status === SubscriptionStatus::Cancelled) {
            throw new DomainException('cancelled subscription cannot be renewed');
        }

        $this->period = $next;
    }
}
Как выбрать границу агрегата. Спроси: «что должно быть верно в один момент времени?» Если правило требует одновременной правки двух объектов, они, скорее всего, один агрегат. Если можно подождать и согласовать событием — это разные агрегаты.

4 Clean Architecture: правило зависимостей

Главная идея — зависимости направлены внутрь. Домен не знает, что его вызывают из HTTP-контроллера, хранят в Postgres и отправляют в Kafka. Он описывает правила, а внешний мир подключается через интерфейсы.

Frameworks & drivers→ Interface adapters→ Use cases→ Entities / Domain

Стрелки — направление зависимостей. Домен в центре и не импортирует ничего из внешних слоёв.

СлойЧто содержитЧего там нет
DomainСущности, значения, агрегаты, события, интерфейсы репозиториевSQL, HTTP, Laravel, Kafka
ApplicationСценарии: опубликовать видео, продлить подпискуБизнес-правил домена и деталей инфраструктуры
Interface adaptersКонтроллеры, презентеры, адаптеры репозиториевСложной доменной логики
InfrastructureLaravel, PDO, Redis, Kafka, внешние APIПравил предметной области

Порты и адаптеры

Порт — интерфейс, который объявляет домен или приложение. Адаптер — реализация порта во внешнем мире. Домен говорит «мне нужен репозиторий видео», инфраструктура отвечает «вот Postgres». Замена Postgres на другую базу не трогает домен.

src/
  Catalog/
    Domain/
      Video.php
      VideoId.php
      VideoRepository.php      // порт
      VideoPublished.php       // доменное событие
    Application/
      PublishVideo/
        PublishVideoHandler.php
    Infrastructure/
      Persistence/
        PostgresVideoRepository.php   // адаптер
      Http/
        PublishVideoController.php

Сценарий приложения тонкий: загрузить агрегат, вызвать доменный метод, сохранить, опубликовать событие. Бизнес-правило «нельзя опубликовать удалённое видео» живёт в домене, а не в контроллере.

Проверка архитектуры. Если доменный класс импортирует `Illuminate`, `PDO` или `RdKafka`, граница протекла. Это ловится статическим анализом и архитектурными тестами.

5 Практика: домен видео-платформы

Выделяем контексты и для каждого — свою модель. Не пытаемся сделать один универсальный `Video` на все случаи.

КонтекстКлючевые понятияСобытия
CatalogВидео, жанр, доступность, обложкаVideoPublished, VideoUnpublished
PlaybackСессия просмотра, качество, DRM, позицияPlaybackStarted, PlaybackHeartbeat
TranscodingЗадача, исходный файл, профиль, статусTranscodeRequested, TranscodeCompleted
BillingПодписка, план, период, платёжSubscriptionRenewed, PaymentFailed
RecommendationsПрофиль интересов, историяRecommendationServed

Агрегаты и границы

  • Video в каталоге — агрегат: метаданные и статус публикации меняются вместе.
  • ViewSession в playback — отдельный агрегат: позиция и качество не должны блокировать каталог.
  • Subscription в биллинге — агрегат: период и статус подписки согласованы.
  • TranscodeJob — агрегат: статус и попытки обработки.

Как связать контексты

Каталог публикует `VideoPublished`, транскодинг запускает обработку, playback получает доступные качества, биллинг проверяет право на просмотр. Связь — через события и явные контракты, а не через общую таблицу.

Артефакт недели. ADR с границами контекстов и диаграмма: какие контексты есть, кто от кого зависит, какие события пересекают границу. Этого достаточно, чтобы обсуждать архитектуру на интервью.

6 Частые ошибки

  • DDD ради DDD. Пять слоёв и мапперы для CRUD-формы. Сложность выросла, правил не прибавилось.
  • Анемичная модель. В классах только геттеры и сеттеры, а правила размазаны по сервисам. Это уже не DDD, а данные сбоку.
  • Гигантский агрегат. Внутрь сложили всё, что связано. Теперь любая правка блокирует всех и требует длинной транзакции.
  • Доменные события как интеграционные. Внутреннее событие улетает наружу без стабильного контракта и версии. Потребители ломаются при рефакторинге.
  • Утечка ORM. Репозиторий возвращает Eloquent-модель, и домен начинает зависеть от фреймворка.
  • Слои ради слоёв. Контроллер вызывает сервис, сервис — менеджер, менеджер — хелпер, и всё это ради одного `SELECT`.
Когда DDD окупается Много бизнес-правил, частые изменения, разные термины у команд, высокая цена ошибки, долгая жизнь продукта.
Когда проще CRUD Мало правил, простая админка, короткий срок жизни, небольшой домен. Здесь достаточно аккуратных сервисов и тестов.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Что такое bounded context и как его выделить?

«Это граница, внутри которой термины и модель имеют одно значение. Выделяю по смене языка и правил: если в каталоге «видео» — карточка, а в транскодинге — файл и профили, это разные контексты. Помогают карта зависимостей, интервью с бизнесом и анализ того, где чаще меняются правила. Границы не должны совпадать с командами один к одному, но часто коррелируют».

Своими словами

Это комнаты в доме: в каждой свои правила и свой смысл слов. Не надо делать одну комнату на всё.

02Чем Entity отличается от Value Object?

«У сущности важна идентичность: два видео с одинаковым названием — разные видео. У значения важна только величина: две суммы 100 рублей равны, и объект неизменяем. Деньги, период, разрешение — value objects с проверками в конструкторе. Это убирает класс ошибок вроде сложения рублей с долларами».

Своими словами

Сущность — «кто это», значение — «сколько это». Сумму можно заменить новой, а пользователя с тем же именем — нельзя.

03Что такое агрегат и как выбрать его границу?

«Агрегат — граница согласованности, изменения идут через корень, одна транзакция — один агрегат. Границу выбираю по инвариантам: что должно быть верно одновременно. Если правило требует правки двух объектов в один момент, это один агрегат; если можно согласовать событием — разные. Слишком крупный агрегат создаёт блокировки и мешает масштабированию».

Своими словами

Это неделимая сделка: либо все изменения внутри согласованы, либо ничего. Всё, что можно досогласовать потом, выносим наружу.

04В чём главное правило Clean Architecture?

«Зависимости направлены внутрь: домен не знает про фреймворк, БД и брокер. Внешние слои зависят от домена, а домен общается с миром через интерфейсы- порты, которые реализуют адаптеры. Это позволяет тестировать правила без инфраструктуры и менять детали, не трогая бизнес-логику».

Своими словами

Правила в центре, инструменты снаружи. Замена базы — это замена адаптера, а не переписывание бизнеса.

05Когда DDD не нужен?

«Когда домен простой и правил мало: CRUD-админка, небольшой сервис, короткий срок жизни. Полноценные слои и агрегаты добавят стоимость без выгоды. В таких местах достаточно аккуратных сервисов, валидации и тестов. DDD вводят там, где сложность правил и цена ошибки оправдывают вложения».

Своими словами

Не надо строить метро в деревне. Для трёх таблиц хватит простого кода.

06Какие ошибки чаще всего допускают при DDD?

«Анемичная модель, гигантские агрегаты, доменные события без контракта, утечка ORM в домен и слои ради слоёв. Ещё — попытка применить DDD к простому CRUD. Признак проблемы: бизнес-правила живут в контроллерах и сервисах, а классы домена только переносят данные».

Своими словами

Самая частая ошибка — сделать много умных слов и ни одного правила в домене.

Ответь вслух, не подглядывая. 0 / 5

Если запомнить одно: DDD — про язык и границы, Clean Architecture — про направление зависимостей. Вместе они делают сложные правила независимыми от инструментов.
