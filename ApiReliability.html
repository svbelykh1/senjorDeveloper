Идемпотентность, дубли и пулинг соединений

Как сделать повторный запрос безопасным, почему дубли — норма, а не баг, и как пул соединений в PHP-FPM может положить базу. Плюс whitelist/blacklist и защита API на входе.

1 Почему повтор — это норма

Клиент не получил ответ и повторил запрос. Балансировщик повторил вызов при таймауте. Kafka доставила событие дважды. Пользователь дважды нажал «Оплатить». В распределённой системе повтор случается всегда, и задача API — сделать его безопасным.

Аналогия Вы отправили письмо и не получили подтверждение. Отправили ещё раз. Хороший получатель понимает, что это то же письмо, а не второе. Плохой — обрабатывает дважды.

На интервью Senior проверяют: понимаешь ли ты разницу между транспортным повтором и бизнес-дублем, умеешь ли реализовать идемпотентность и не устроить переполнение пула соединений.

Главная мысль. Надёжность строится не на «запрос придёт один раз», а на «повторный запрос не изменит результат».

2 Идемпотентность

Идемпотентная операция при повторе даёт тот же результат, что и при первом вызове. `GET` идемпотентен по смыслу. `POST /payment` — нет, поэтому ему нужен Idempotency-Key.

Как это работает

  1. Клиент генерирует ключ и передаёт его в заголовке.
  2. Сервер ищет ключ в хранилище. Если есть — возвращает сохранённый ответ.
  3. Если нет — фиксирует ключ, выполняет операцию, сохраняет результат.
  4. Повтор с тем же ключом не выполняет операцию заново.
  5. Тот же ключ с другим телом — ошибка `409` или `422`.
CREATE TABLE idempotency_keys (
  user_id      bigint      NOT NULL,
  key          text        NOT NULL,
  request_hash text        NOT NULL,
  status       text        NOT NULL,  -- processing | done | failed
  response     jsonb,
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)
);

Уникальный ключ в базе — главный механизм. Даже если два запроса пришли одновременно, один вставит запись, второй получит конфликт и подождёт результат. Запись ключа и бизнес-операция должны быть согласованы: либо одна транзакция, либо статус `processing` и повторная проверка.

Срок жизни ключа. Хранить вечно дорого. Обычно 24 часа или столько, сколько клиент может повторять. После TTL повтор будет воспринят как новая операция — это нужно понимать.

3 Дубли и дедупликация

Откуда берутся дубли

  • Клиент повторил запрос после таймаута.
  • Балансировщик повторил вызов.
  • Продюсер Kafka повторил отправку.
  • Consumer упал после обработки, но до коммита offset.
  • Пользователь нажал кнопку дважды.

Как защититься

УровеньПриём
HTTPIdempotency-Key, повтор с тем же ключом
БазаUnique constraint, `INSERT ... ON CONFLICT DO NOTHING`
ConsumerПроверка `event_id` в таблице обработки
БизнесПроверка состояния: платёж уже проведён, подписка уже активна
UIБлокировка кнопки, но не как единственная защита

Идемпотентный consumer обычно хранит `event_id` и результат обработки в одной транзакции с бизнес-изменением. Тогда повторная доставка видит запись и сразу выходит.

Exactly-once на практике. Внешние системы не участвуют в транзакции Kafka, поэтому «ровно один раз» end-to-end не гарантируется. Гарантируют at-least-once и делают обработку идемпотентной.

4 Пулинг соединений

Соединение с БД или Redis — дорогой ресурс. Открывать его на каждый запрос накладно, держать бесконечно — опасно. Пул переиспользует соединения и ограничивает их число.

PHP-FPM

Каждый worker PHP-FPM держит своё соединение с Postgres. Если `pm.max_children` = 50 и каждый worker открывает по соединению, базе нужно минимум 50 слотов. Несколько сервисов легко превышают `max_connections`, и новые подключения начинают падать.

  • PgBouncer в transaction mode снижает число реальных соединений.
  • Persistent connections экономят время, но занимают слот навсегда.
  • Таймауты обязательны: соединение без таймаута висит и блокирует воркер.
  • Мониторинг занятости пула и очереди на подключение.

HTTP и gRPC

HTTP keep-alive переиспользует TCP-соединения; пул на клиенте ограничивает параллелизм. gRPC использует один канал с мультиплексированием — не нужно открывать соединение на каждый вызов. Главное — не создавать клиент в цикле.

Ошибка масштабирования. Увеличили число pod'ов, каждый под поднял пул — база получила в N раз больше соединений. Пул нужно считать на весь кластер, а не на один экземпляр.

5 Whitelist и blacklist

ПодходПринципПлюсМинус
BlacklistЗапрещаем известных нарушителейПросто, не мешает остальнымОбходится новым IP или доменом
WhitelistРазрешаем только известныхБезопасно по умолчаниюТребует сопровождения списка

Blacklist удобен для быстрых блокировок, но не является защитой: атакующий меняет адрес. Whitelist надёжнее для админки, внутренних API и партнёрских интеграций. На практике их сочетают с rate limiting, API-ключами и WAF.

Правила на gateway

  • Аутентификация до бизнес-логики.
  • Лимит по пользователю, IP и эндпоинту.
  • Whitelist для административных маршрутов.
  • Blacklist для подтверждённых злоупотреблений.
  • Логирование отказов и алерты на всплеск.
CORS — не контроль доступа. Он ограничивает браузер, но не защищает API от прямых запросов. Авторизация должна быть на сервере.

6 Практика: платёжный эндпоинт

POST /payments
Idempotency-Key: 3f9c1a2e-...
Content-Type: application/json

{ "order_id": 42, "amount": 1490, "currency": "RUB" }
  1. Проверить ключ и хэш тела. Если ключ есть и хэш совпадает — вернуть сохранённый ответ.
  2. Если ключ есть, а тело другое — `409 Conflict`.
  3. Вставить запись `processing` с уникальным ключом.
  4. Провести платёж и записать результат в ту же запись.
  5. При повторе вернуть тот же ответ, не вызывая провайдера снова.
  6. Хранить ключи 24 часа, затем удалять по расписанию.

Дополнительно: unique constraint на `order_id`, чтобы даже при потере ключа не создать второй платёж. И статус платежа, по которому можно проверить, не проведён ли он уже.

Что показать на интервью. «Idempotency-Key + unique constraint в БД, сохранение ответа, проверка хэша тела и TTL. Для consumer — таблица обработанных event_id. Для пула — PgBouncer и расчёт на весь кластер, а не на один pod».

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Как реализовать идемпотентность для `POST /payment`?

«Клиент передаёт Idempotency-Key. Сервер хранит ключ, хэш тела и результат в таблице с уникальным индексом. Первый запрос выполняет платёж и сохраняет ответ; повтор с тем же ключом возвращает сохранённый ответ. Тот же ключ с другим телом — ошибка. Плюс unique constraint на `order_id` как вторая линия защиты».

Своими словами

Запоминаем номер операции: второй раз с тем же номером просто отдаём прошлый результат.

02Откуда берутся дубли и как от них защититься?

«Из повторов клиента, балансировщика, продюсера и consumer'а после сбоя. Защита на разных уровнях: Idempotency-Key в HTTP, unique constraint в БД, проверка `event_id` в consumer'е, проверка бизнес-состояния. UI-блокировка кнопки полезна, но не заменяет серверную защиту».

Своими словами

Повтор — не исключение, а правило. Значит, операция должна быть безопасной при повторе.

03Почему exactly-once трудно достичь?

«Kafka-транзакция может гарантировать exactly-once внутри Kafka, но не покрывает запись в Postgres, вызов платёжного провайдера и отправку письма. Эти системы не участвуют в одной транзакции. Поэтому на практике — at-least-once и идемпотентная обработка».

Своими словами

Можно гарантировать один раз внутри одного шкафа, но не во всём городе.

04Как пул соединений в PHP-FPM может положить базу?

«Каждый worker держит соединение. При `max_children` = 50 и нескольких сервисах число соединений превышает `max_connections` Postgres, и новые подключения падают. Решение — PgBouncer в transaction mode, расчёт пула на весь кластер, таймауты и мониторинг занятости. При масштабировании pod'ов пул умножается».

Своими словами

Каждый официант держит свой телефон, и коммутатор не выдерживает. Нужен общий пул.

05Чем whitelist отличается от blacklist и почему одного мало?

«Blacklist запрещает известных нарушителей, но обходится новым IP. Whitelist разрешает только известных и безопасен по умолчанию, но требует сопровождения. На практике сочетают: whitelist для админки и партнёров, blacklist для подтверждённых атак, плюс rate limiting и WAF».

Своими словами

Чёрный список — «этим нельзя», белый — «только этим можно». Второй надёжнее, но список надо вести.

06Как проверить, что защита работает?

«Повторным запросом с тем же ключом, конкурентными запросами, повторной доставкой события, тестом на другой хэш тела и тестом на истечение TTL. Плюс метрики: доля повторов, конфликты ключей, занятость пула, ошибки подключения. Без нагрузки защита может выглядеть рабочей, но не быть ею».

Своими словами

Надо специально нажать дважды и отправить событие повторно — иначе не узнать.

Ответь вслух, не подглядывая. 0 / 5

Если запомнить одно: повторяемость — свойство системы, а не ошибка клиента. Делай операции идемпотентными, а пулы — ограниченными.
