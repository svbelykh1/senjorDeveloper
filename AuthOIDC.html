OAuth 2.0, OIDC, PKCE и управление доступом

1 Аутентификация и авторизация

Аутентификация отвечает на вопрос «кто ты». Авторизация — «что тебе можно». Это разные задачи, и путать их опасно: успешный логин не означает право на любое действие.

Аналогия Паспорт подтверждает, кто вы. Пропуск на этаж говорит, куда можно пройти. Паспорт без пропуска не открывает серверную.

OAuth 2.0 — про делегированный доступ: пользователь разрешает приложению действовать от своего имени, не передавая пароль. OIDC (OpenID Connect) — надстройка над OAuth, которая добавляет аутентификацию и профиль: кто пользователь и какие у него базовые данные.

Главная мысль. OAuth — это не «логин через Google». Это протокол выдачи токенов доступа. OIDC добавляет к нему личность.

2 OAuth 2.0: роли и Authorization Code + PKCE

РольКто этоПример
Resource ownerВладелец данныхПользователь
ClientПриложение, которому дают доступВеб- или мобильный клиент
Authorization serverВыдаёт токеныKeycloak, Auth0, корпоративный SSO
Resource serverAPI, который проверяет токенPlayback API

Authorization Code + PKCE

  1. Клиент генерирует `code_verifier` и `code_challenge = SHA256(verifier)`.
  2. Отправляет пользователя на authorization server с `challenge`, `client_id`, `redirect_uri` и `scope`.
  3. Пользователь входит и подтверждает доступ.
  4. Сервер возвращает `code` на зарегистрированный `redirect_uri`.
  5. Клиент меняет `code` + `verifier` на токены.
  6. Сервер проверяет, что хэш совпадает, и выдаёт access/refresh/ID токены.

Зачем PKCE. Код авторизации может перехватить вредоносное приложение на устройстве. Без `verifier` украденный код бесполезен: обменять его на токен не получится. PKCE обязателен для публичных клиентов (SPA, мобильные) и рекомендуется для всех.

Implicit flow устарел. Он отдаёт access token прямо в URL и плохо защищён. Современный выбор — Authorization Code + PKCE. Для машин без пользователя — client credentials.

3 OIDC: три токена и их роли

ТокенДля чегоКому
Access tokenДоступ к APIResource server
ID tokenКто пользователь, базовый профильКлиенту, не для API
Refresh tokenПолучить новый access tokenКлиенту, хранить максимально защищённо

ID token — это JWT с claims: `sub`, `iss`, `aud`, `exp`, `email`, `name`. Его проверяет клиент, чтобы понять, кто вошёл. Access token проверяет API; он может быть JWT или непрозрачной строкой, тогда API спрашивает introspection у authorization server.

Где хранить

  • Refresh token — в `httpOnly`, `Secure`, `SameSite` cookie или в защищённом хранилище ОС. Не в `localStorage`, если можно иначе.
  • Access token — в памяти вкладки, короткий TTL.
  • Никогда — в URL, логах, аналитике и репозитории.

Refresh-токены стоит ротировать: при каждом использовании выдавать новый, а старый помечать использованным. Если старый пришёл повторно — это признак кражи, всю цепочку отзывают.

OIDC discovery. Сервер публикует `.well-known/openid-configuration` с адресами эндпоинтов и JWKS. Клиенту не нужно хардкодить ключи: он забирает публичные ключи и проверяет подпись.

4 JWT: что проверять

JWT — подписанный набор claims. Он подписан, но не зашифрован: любой может прочитать содержимое. Секреты и лишние персональные данные в payload не кладут.

Обязательные проверки

  • Подпись по ключу из JWKS; алгоритм — из allowlist, а не из заголовка токена.
  • iss — ожидаемый issuer.
  • aud — этот API, а не другой.
  • exp / nbf / iat — срок действия и допустимый разброс.
  • scope / roles — достаточно ли прав для операции.
// Псевдокод проверки
$payload = Jwt::decode($token, $publicKey, ['RS256']);

if ($payload->iss !== 'https://sso.example.com') throw new Unauthorized();
if ($payload->aud !== 'playback-api')             throw new Unauthorized();
if ($payload->exp < time())                       throw new Unauthorized();
Не принимай `alg: none`. И не позволяй клиенту выбирать алгоритм. Иначе токен можно подделать. Всегда фиксируй допустимые алгоритмы на сервере.

5 ACL, RBAC и ABAC

МодельИдеяКогдаМинус
ACLПрава на конкретный объектФайлы, документы, видеоМного записей, сложно администрировать
RBACПрава через ролиКоманды, админка, типовые ролиРоли разрастаются, нет контекста
ABACПравила по атрибутамМультитенантность, регион, тарифСложно тестировать и объяснять

Пример для видео: RBAC — роль `editor` может публиковать видео. ABAC — редактор может публиковать только в своём регионе и только для своего тарифа. ACL — конкретному пользователю выдан доступ к конкретному приватному видео.

Проверка прав должна быть на сервере, в одном месте, до выполнения операции. Скрытая кнопка в интерфейсе — это UX, а не защита.

Принцип наименьших привилегий. По умолчанию запрещено, разрешение выдаётся явно. Для сервисных аккаунтов — только нужные scopes, а не «всё».

6 Практика: auth-flow видео-сервиса

  1. Вход. Веб-клиент идёт в OIDC-провайдер по Authorization Code + PKCE.
  2. Токены. Access — 15 минут, ID — для профиля, refresh — 30 дней с ротацией.
  3. Хранение. Refresh в `httpOnly` cookie, access в памяти.
  4. API. Playback проверяет JWT: подпись, iss, aud, exp, scope.
  5. Права. RBAC для ролей, ABAC для региона и тарифа, ACL для приватных видео.
  6. Сервис-сервис. Client credentials с узкими scopes, без пользовательского контекста.
  7. Отзыв. Короткий TTL, ротация refresh, denylist по `jti` для критичных случаев.
Что показать на интервью. Нарисуй поток кодом обмена, назови три токена и их назначение, объясни PKCE и проверки JWT. Затем добавь модель доступа и принцип наименьших привилегий.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Чем OAuth 2.0 отличается от OIDC?

«OAuth 2.0 — про делегированный доступ: выдаёт токены, чтобы приложение могло вызывать API от имени пользователя. OIDC — надстройка, которая добавляет аутентификацию: ID token с данными пользователя и стандартные эндпоинты. OAuth отвечает «что можно», OIDC — ещё и «кто ты»».

Своими словами

OAuth даёт ключ от комнаты, OIDC ещё и говорит, чей это ключ.

02Зачем нужен PKCE в Authorization Code flow?

«PKCE защищает код авторизации от перехвата. Клиент создаёт случайный `verifier`, отправляет его хэш в запросе, а при обмене кода предъявляет сам `verifier`. Украденный код без него не обменять на токен. Особенно важно для публичных клиентов: SPA и мобильных приложений, где секрет клиента не сохранить».

Своими словами

Код бесполезен без второй половинки, которая осталась у клиента.

03Чем access, ID и refresh токены отличаются?

«Access token — для вызова API, его проверяет resource server. ID token — для клиента, чтобы узнать пользователя; в API его не отправляют. Refresh token — чтобы получить новый access без повторного логина, хранится максимально защищённо и ротируется. Сроки: access короткий, refresh длинный».

Своими словами

Access — пропуск в зал, ID — бейдж с именем, refresh — право получить новый пропуск.

04Где хранить токены в браузере?

«Refresh — в `httpOnly`, `Secure`, `SameSite` cookie, чтобы JavaScript не мог прочитать. Access — в памяти вкладки с коротким TTL. `localStorage` удобен, но доступен XSS, поэтому для долгоживущих токенов нежелателен. В URL и логах токены не хранят никогда».

Своими словами

Долгий ключ — в закрытом ящике, короткий — в руке, и никогда на видном месте.

05Что проверять в JWT на стороне API?

«Подпись по публичному ключу из JWKS, алгоритм из allowlist, `iss`, `aud`, `exp`, `nbf`, `iat`, а также scope или роли. JWT только подписан, не зашифрован, поэтому секреты и лишние PII в него не кладу. При критичных действиях учитываю отзыв через `jti` и короткий TTL».

Своими словами

Проверяем печать, срок, кому выдан и что разрешено. Читать токен может каждый, поэтому секретов там нет.

06RBAC или ABAC: что выбрать?

«RBAC — когда права определяются ролью: админ, редактор, зритель. ABAC — когда важен контекст: регион, тариф, владелец, время. Часто совмещают: роль даёт базовые права, атрибуты сужают их. ACL — для прав на конкретный объект. Проверка всегда на сервере, по принципу наименьших привилегий».

Своими словами

RBAC — «кто ты по должности», ABAC — «что разрешено в этой ситуации».
