1 Что именно проверяют

Формулировки взяты из матрицы компетенций, уровень 3 — «Уровень опыта».

БлокФормулировка
ЗНАЕТ Принципы управления рабочим процессом в Jira или другом инструменте. Категории оценки трудозатрат разработки, может назвать несколько инструментов и методик
УМЕЕТ Вести техническую документацию. Брать на себя ведущую роль в команде по Scrum и проводить планирование
Не требуется (Staff) KPI команды, аудит процессов, точная оценка целого продукта, GitFlow как стандарт организации
Как выглядит сильный ответ за 60 секунд: «У нас Scrum, статусы от Backlog до Done, переходы ограничены правилами: в Code Review может перевести только автор, из Code Review — только ревьюер, в Done нельзя без привязанного MR. Оцениваем в story points через planning poker, для рискованных задач используем spike и три точки. В оценку закладываем не только код, но и review, тесты, интеграции, деплой и буфер на риски — иначе стабильно занижаем в полтора-два раза».

2 Jira workflow

Анатомия

Workflow — это не список статусов, а граф переходов с правилами. Четыре слоя, которые надо назвать:

  1. Issue type — Epic, Story, Task, Sub-task, Bug, Spike, Incident
  2. Statuses — где задача находится
  3. Transitions — между какими статусами можно перейти
  4. Transition rules — что проверяется и что происходит при переходе

Правила перехода — это то, что отличает senior-ответ от junior:

Тип правилаЧто делаетПример
ConditionКто может нажатьПереход в Code Review — только автор; из Code Review — только reviewer
ValidatorЧто должно быть выполненоНельзя в Done без привязанного MR; нельзя в QA без заполненного Test plan
Post-functionЧто произойдёт автоматическиНазначить ревьюера, проставить дату, дёрнуть webhook в CI

Рабочий пример для backend-команды

Backlog→ Ready for Dev→ In Progress→ Code Review→ QA→ Ready for Release→ Done

Плюс отдельные статусы: Blocked и Reopened. Blocked — статус, а не комментарий.

Почему именно так:

  • Ready for Dev — точка, где срабатывает Definition of Ready. Без неё команда начинает спринт с задачами, которые ещё не готовы к работе.
  • Code Review отдельно от In Progress — иначе непонятно, где задача стоит в очереди на ревью, и она «висит в работе» неделю.
  • QA отдельно — не потому что есть отдельный QA, а чтобы был виден этап проверки и не терялись баги.
  • Ready for Release — буфер между «сделано» и «в проде», если релизы не непрерывные.
  • Blocked — отдельный статус, иначе блокеры не видно ни на доске, ни в метриках.

Типы задач

ТипКогда используется
EpicКрупная фича или квартальная инициатива
StoryПользовательская ценность, формулируется через «как пользователь…»
TaskТехническая работа без прямой пользовательской ценности
Sub-taskДекомпозиция Story или Task до ≤1–2 дней
SpikeИсследование с таймбоксом, результат — решение, а не код
BugОтклонение от ожидаемого поведения
IncidentПрод-инцидент, часто с отдельным SLA и процессом

Поля, которые реально работают

  • components — сервис или домен: video-catalog, playback, billing
  • labels — сквозные метки: tech-debt, security, p1
  • fixVersion / affectsVersion — в каком релизе исправлено / где воспроизводится
  • story points — относительная оценка
  • linked issues — blocks / is blocked by / relates to; важно для зависимостей между сервисами

Доска и метрики

МетрикаЧто показываетКак использовать
VelocityСколько команда закрывает за спринтТолько для прогноза. Не KPI
Cycle timeОт «в работе» до «готово»Показывает, где задача застревает
Lead timeОт создания до «готово»Отражает ожидание пользователя
Cumulative FlowНакопление задач по статусамРост полосы = растёт WIP, скоро bottleneck
Control chartРазброс cycle timeПоказывает стабильность процесса

Scrum-доска: спринты, burndown, velocity. Kanban: непрерывный поток, WIP-лимиты, cycle time. WIP-лимит — главный инструмент против «в работе 15 задач одновременно».

JQL — минимум, который стоит помнить

project = VIDEO AND status = "In Progress" AND assignee = currentUser()
sprint in openSprints() AND issuetype = Bug
status changed to Done during (startOfWeek(-4), now())

Достаточно уметь объяснить, что JQL — это фильтр по полям, и привести 2–3 примера.

Time tracking в Jira

Три поля, которые часто путают:

  • Original estimate — оценка до начала работ
  • Remaining estimate — сколько ещё осталось; обновляется по ходу
  • Time spent — сумма по worklog'ам
Если требовать заполнять worklog каждый день, люди начинают «рисовать» часы. Оценка и учёт времени — разные инструменты: оценка нужна команде для планирования, учёт — для отчётности. Смешивать их вредно.

Антипаттерны — назови хотя бы три

  • Статусы-декорации: «Dev Done», «Dev Done Done», «Testing 2»
  • Нет Definition of Done → задача «готова», но не задеплоена и без тестов
  • WIP без лимита
  • Задачи на две недели — прогресс невозможно измерить
  • Workflow у каждой команды свой без причины
  • Оценка превращена в обещание и используется для наказания
Отдельный материал: Scrum и Kanban — определения, устройство и различия. Эти подходы относятся к той же компетенции «Жизненный цикл разработки ПО».

3 Оценка трудозатрат

Три оси категорий

Самый частый провал на интервью: человек говорит «оцениваю в story points» и всё. Нужно показать, что категорий несколько.

Ось A. По типу работ — что вообще входит в оценку

КатегорияТипичная доля
Анализ и уточнение требований5–10%
Проектирование5–15%
Разработка40–50%
Code review5–10%
Тесты: unit, integration, ручные15–20%
Интеграция и зависимости5–15%
Деплой, фича-тоглы, миграции5%
Документация2–5%
Мониторинг, алерты, наблюдаемость5%
Буфер на риски10–20%
«Оценка — это не только код. Если не заложить review, тесты, деплой и риски, она всегда занижена — обычно в 1,5–2 раза».

Ось B. По уровню неопределённости

  • Known — делал похожее, есть reference story → обычная оценка
  • Known unknown — понятно, чего не знаем → spike с таймбоксом 0,5–1 день
  • Unknown unknown — не понимаем масштаб → диапазон и исследование, а не точка

Ось C. По единицам измерения

  • Story points — относительные, Fibonacci
  • Ideal hours / man-days — абсолютные, но зависят от человека
  • T-shirt sizes — S/M/L/XL, для грубого бэклога
  • Buckets — ≤1 дня / 1–3 / 3–5 / >5

Методы — назови 4–5 и выбери под ситуацию

МетодКогда применятьОграничение
Expert judgmentЗнакомая область, есть опытСубъективно, зависит от одного человека
Analogy / reference storyЕсть похожая задачаНужна база reference stories
Bottom-up (WBS)Комплексная задачаДорого по времени, нужна декомпозиция
Top-downРано, грубо, для roadmapНизкая точность
Three-point / PERTВысокая неопределённостьНужны три оценки, а не одна
Planning pokerКомандная оценка в спринтеДолго для большого бэклога
Wideband DelphiЭкспертная оценка без группыДорого
Bucket systemБольшой бэклог, много людейГрубо
#NoEstimatesСтабильный поток, мелкие задачиНе везде применимо
PERT: E = (O + 4M + P) / 6 σ = (P − O) / 6

Хорошо звучит на интервью: «для рискованных кусков считаю три точки, а не одну».

Конус неопределённости

Точность оценки зависит от стадии, а не от старания:

  • Идея / концепт: ×0,25 – ×4
  • Согласованные требования: ×0,5 – ×2
  • Дизайн готов: ×0,8 – ×1,25
  • Реализация начата: ±10–20%
Сильный ответ: «на ранней стадии я даю диапазон и называю допущения, а не точное число».

Story points vs часы

  • SP относительны и не конвертируются в часы
  • Velocity — внутрикомандный инструмент прогноза, не метрика производительности
  • Если нужны часы (подряд, отчётность) — давай диапазон и фиксируй допущения
  • Использование velocity как KPI разрушает оценку: команда начинает завышать SP

Алгоритм оценки комплексной задачи

Это то, что стоит рассказать на интервью как свой процесс:

  1. Выписать критерии приёмки и нефункциональные требования
  2. Декомпозировать до кусков ≤1–2 дней; если кусок больше — резать дальше
  3. Для каждого куска: знакомо? есть reference?
  4. Неизвестное — spike с таймбоксом, а не «заложим побольше»
  5. Оценить втроём: автор, исполнитель, тестировщик
  6. Для рискованных кусков — три точки
  7. Добавить явно: review, тесты, миграции, фича-тоглы, деплой, мониторинг
  8. Буфер на риски 10–20%, а не «на всякий случай 50%»
  9. Зафиксировать допущения и зависимости в задаче
  10. Пересмотреть после spike или первого дня работы

Пример на домене видео

Задача: «Кэшировать каталог видео в Redis с инвалидацией по событию из Kafka».

РаботаДни
Анализ и дизайн ключей, TTL, стратегии инвалидации0,5
Реализация кэша (Cache-Aside)1,5
Consumer инвалидации + идемпотентность1,0
Unit + integration тесты1,0
Code review0,25
Нагрузочный тест0,5
Фича-тогл, деплой, откат0,5
Метрики и алерты на hit ratio0,5
Буфер на риски ~15%0,8
Итого≈6,5–7 дней
Смысл примера: «в коде это полтора дня». Именно этот разрыв чаще всего и приводит к провалу оценки. Хороший ответ на интервью — показать такую разбивку, а не назвать одно число.

4 Вопросы и модельные ответы

Два блока на каждый вопрос: модельный ответ — структура и формулировки для интервью, и «своими словами» — как это звучит вживую, без канцелярита.

01Как устроен ваш workflow в Jira?

«У нас Scrum. Статусы: Backlog → Ready for Dev → In Progress → Code Review → QA → Ready for Release → Done, плюс Blocked. Переход в Code Review только автором, из Code Review — только ревьюером. В Done нельзя без привязанного MR, это валидатор. DoR фиксирует, что задача готова к спринту, DoD — что она реально закрыта: код в master, тесты зелёные, задеплоено, метрики есть».

Своими словами

У нас всё довольно обычно: бэклог, готово к разработке, в работе, ревью, тесты, готово к релизу, готово. Плюс Blocked. Самое полезное — что из ревью задачу может вытащить только ревьюер, а в Done не перевести, пока не привязан MR. Иначе статусы быстро превращаются в декорацию: все двигают, никто не проверяет.

02Чем story points отличаются от часов?

«SP относительны: они измеряют сложность, неопределённость и объём относительно других задач команды. В часы не конвертируются. Velocity нужна для прогноза, а не для сравнения людей — иначе команда начинает играть с оценками».

Своими словами

Сторипоинты — это не часы, переводить их в часы бессмысленно. Ими сравниваю задачи между собой: вот эта примерно как та, что была в прошлом спринте. Велосити нужна только чтобы прикинуть, сколько влезет в спринт. Как только её начинают сравнивать между командами или тащить в отчёты — оценка умирает, все начинают завышать.

03Как оценить задачу с высокой неопределённостью?

«Сначала отделяю известное от неизвестного. На неизвестное ставлю spike с таймбоксом полдня-день. Дальше оцениваю тремя точками и даю диапазон с явными допущениями. Если и после spike непонятно — режу задачу на меньшие части, а не увеличиваю буфер».

Своими словами

Если задача непонятная, я не пытаюсь оценить её «посильнее». Беру полдня-день на spike, чтобы понять, что внутри. После этого либо оценка становится нормальной, либо задача режется. Наращивать буфер — худшее, что можно сделать: он всё равно не спасает, а сроки раздувает.

04Какие категории работ включаете в оценку?

«Не только разработку: анализ, дизайн, review, тесты, интеграции, деплой, документацию, мониторинг и буфер на риски. Без этого оценка занижается в полтора-два раза — это видно по факту».

Своими словами

По факту в оценку идёт не только код. У меня в последнем проекте полтора дня кода превратились в неделю: тесты, ревью, миграция, фича-тогл, деплой, дашборд. Поэтому я всегда явно проговариваю: вот это разработка, вот это тесты, вот это выкатка, вот это риски. Иначе потом «почему так долго».

05Что такое Definition of Ready и Definition of Done?

«DoR — задача готова к работе: есть критерии приёмки, оценка, зависимости, понятен способ проверки. DoD — задача действительно закрыта: код в основной ветке, тесты проходят, задеплоено, документация и метрики на месте. DoR защищает от старта сырых задач, DoD — от «готово, но не работает»».

Своими словами

DoR — это когда задачу можно брать, а не «вроде понятно». Есть критерии приёмки, оценка, понятно, как проверять. DoD — когда реально готово: влито, задеплоено, тесты зелёные. У нас раньше «готово» значило «код написан», и это каждый раз вылезало на релизе.

06Как понять, что процесс деградирует?

«По Cumulative Flow: растёт полоса WIP — значит, задачи копятся в работе. По cycle time: если растёт при стабильном объёме, где-то bottleneck. По разнице lead time и cycle time: много времени уходит до старта работы, то есть проблема в приоритизации, а не в разработке».

Своими словами

Смотрю на доску и на цифры. Если в работе висит двадцать задач — это уже не «мы быстрые», это WIP. Если cycle time растёт, а объём тот же — ищу, где застревает: ревью, тесты, ожидание инфры. И отдельно смотрю, сколько задача лежит до старта: часто проблема не в разработке, а в том, что её месяц не брали.

07Scrum или Kanban?

«Scrum — когда есть крупные фичи и нужна синхронизация по спринтам. Kanban — когда поток непрерывный: поддержка, инциденты, много мелких задач. Часто гибрид: Scrum для продуктовой работы, Kanban-доска для дежурства».

Своими словами

Scrum беру, когда есть крупные фичи и нужны спринты, чтобы синхронизироваться. Kanban — когда поток: поддержка, инциденты, мелкие правки, там спринты только мешают. У нас было гибридно: продукт в Scrum, дежурство на Kanban-доске с WIP-лимитом.

08Что делать, если оценка не сошлась с фактом?

«Разбираю не «кто виноват», а где именно разошлось: не учли интеграцию, недооценили тесты, был блокер. Фиксирую как reference story, чтобы следующая похожая задача оценивалась точнее. Оценка — это инструмент обучения, а не обещание».

Своими словами

Смотрю, где именно разошлось. Обычно дело не в «плохо оценили», а в том, что забыли интеграцию, тесты или ждали другую команду. Записываю как reference, чтобы в следующий раз похожее оценивать по факту, а не по ощущениям. И стараюсь не превращать оценку в обещание — иначе все начинают закладывать сверху.

5 Самопроверка

Ответь вслух, без подглядывания. Если на любой вопрос уходит больше 60 секунд — тема не закрыта. 0 / 6

Задание на неделю (2–3 часа): возьми свою последнюю задачу, которую оценивал, и разложи её по таблице из примера выше. Сравни сумму с фактическим временем. Найди, какая категория работ была не учтена. Это и будет твоя reference story для интервью.
