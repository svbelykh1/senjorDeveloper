GitLab: protected branches, MR approvals и CI pipelines

Как GitLab не даёт сломать основную ветку, заставляет коллег одобрить изменения и автоматически проверяет код перед merge. Простыми словами, с настройками и примерами.

1 Зачем это нужно

GitLab — это не просто место, где лежит код. Это система, которая мешает случайно сломать основную ветку: не пускает напрямую в main, требует одобрения коллег и автоматически запускает проверки перед merge.

МеханизмЧто защищаетАналогия
Protected branch В важную ветку нельзя пушить напрямую и нельзя переписать историю Дверь с охраной: просто так не пройти
MR approvals Изменения должны одобрить коллеги, а не сам автор Подписи на пропуске
CI pipeline Код автоматически проверяется: тесты, статический анализ, сборка Конвейер с ОТК: брак дальше не едет
Сила — в комбинации. Protected branch без обязательного pipeline и approvals остаётся формальностью: свой MR можно смержить самому, не дожидаясь проверок. На интервью важно показать, что ты настраиваешь все три вещи вместе.

2 Как устроен процесс

Issue → Ветка → Коммиты → Merge Request → Pipeline → Review + approvals → Merge → Deploy

Ветка живёт отдельно, в основную попадает только через MR.

  1. Задача. Issue описывает, что и зачем делаем.
  2. Ветка от main. Например, feature/123-player-retry.
  3. Коммиты. Маленькие и с понятными сообщениями.
  4. Merge Request. Сначала Draft, пока работа не готова к ревью.
  5. Pipeline. Автоматически проверяет код на каждом новом коммите.
  6. Review и approvals. Коллеги смотрят код и ставят одобрение.
  7. Merge. Только когда pipeline зелёный и approvals собраны.
  8. Deploy. Автоматически или по кнопке — зависит от окружения.

Слова, которые пригодятся

ТерминПростыми словами
ProjectПроект в GitLab: репозиторий плюс настройки, задачи, pipeline
BranchОтдельная линия изменений, чтобы не трогать main
Merge Request (MR)Заявка «влейте мою ветку в main, вот изменения»
PipelineВесь конвейер проверок по стадиям

3 Protected branches: дверь с охраной

Идея на пальцах main — это общая ветка, по которой все ориентируются. Если каждый сможет пушить в неё напрямую, одна ошибка сломает сборку у всей команды. Protected branch закрывает прямой вход: изменения только через MR, с проверками и одобрением.

Что можно запретить

  • Прямой push — изменения только через Merge Request.
  • Force push — нельзя переписать историю и «потерять» чужие коммиты.
  • Удаление ветки — main нельзя случайно снести.
  • Merge без проверок — требовать зелёный pipeline и approvals.

Где настроить

Settings → Repository → Protected branches. Для каждой ветки или шаблона (main, release/*) выбираются роли:

НастройкаЧто означает
Allowed to mergeКто может нажать Merge, когда проверки пройдены
Allowed to push and mergeКто может пушить напрямую, минуя MR. Для main — No one
Allowed to force pushПочти всегда выключено
Require approval from code ownersНужно одобрение владельцев затронутых файлов
Status checks must succeedБез зелёного pipeline merge недоступен

Отдельно защищают теги релизов: чтобы никто не перезаписал v1.42.0 другим кодом.

Частая дыра. Ветка защищена, но у maintainer'ов оставлен прямой push «на всякий случай». В итоге проверки обходят именно в тот момент, когда спешат. Если правило есть — оно должно действовать для всех.

4 MR approvals: подписи на пропуске

Идея на пальцах Merge Request — это заявка на вливание ветки. Approval — формальное «я посмотрел, согласен». Пока нужное число подписей не собрано, кнопка Merge не сработает.

Что настраивается

Settings → Merge requests → Approvals. Набор параметров зависит от тарифа GitLab, но логика везде одна:

  • Сколько approvals нужно — например, один или два.
  • Кто может одобрять — конкретные люди, группа или code owners.
  • Автор не одобряет сам себя — иначе смысла в проверке нет.
  • Сброс approvals при новом коммите — если код изменился, подписи собираются заново.
  • Pipeline обязателен — merge только после зелёных проверок.
  • Все обсуждения закрыты — нельзя мержить с открытыми комментариями.

Как выглядит работа

  1. Открываешь Draft MR, пока работа не готова: коллеги не тратят время.
  2. Когда готово — снимаешь Draft и добавляешь reviewers.
  3. Pipeline проверяет код, ревьюеры оставляют комментарии.
  4. Исправляешь замечания. Если включён сброс — approvals нужно получить заново.
  5. Когда pipeline зелёный и approvals собраны — Merge.

Полезные настройки MR: Squash commits (один аккуратный коммит вместо десяти), Delete source branch (ветка не копится), Merge when pipeline succeeds (автоматический merge после проверок).

Approval ≠ review. Галочку можно поставить за две секунды, не открывая diff. Поэтому в команде нужен короткий чек-лист: тесты, миграции, обработка ошибок, безопасность, план отката. Иначе approvals создают ощущение контроля, не давая его.

5 CI pipelines: конвейер проверок

Идея на пальцах Pipeline — это конвейер на заводе. Деталь проходит стадии: собрали, проверили, прогнали тесты, отправили дальше. Если на любой стадии брак — дальше она не едет.

Pipeline описывается файлом .gitlab-ci.yml в корне репозитория. Внутри — стадии и задания. Задания выполняют runner'ы: отдельные машины или контейнеры, зарегистрированные в GitLab.

Минимальный пример

stages: [test, deploy]

unit:
  stage: test
  image: registry.example.com/php-ci:8.3
  script:
    - composer install --no-interaction --prefer-dist
    - vendor/bin/phpunit

Рабочий пример для PHP-сервиса

stages: [test, quality, deploy]

# не запускать два pipeline на один MR
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'

default:
  image: registry.example.com/php-ci:8.3
  cache:
    key:
      files: [composer.lock]
    paths: [.composer-cache/]
  before_script:
    - composer install --no-interaction --prefer-dist

unit:
  stage: test
  script:
    - vendor/bin/phpunit --coverage-text
  artifacts:
    when: always
    expire_in: 1 week
    paths: [coverage/]

static:
  stage: quality
  script:
    - vendor/bin/phpstan analyse --no-progress

deploy:
  stage: deploy
  needs: [unit, static]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  environment:
    name: production
    url: https://video.example.com
  script:
    - ./deploy.sh
  when: manual

Что здесь важно:

  • workflow:rules убирает двойной запуск: отдельно для MR и отдельно для ветки.
  • cache хранит зависимости Composer между запусками — экономит минуты.
  • artifacts сохраняет отчёт о покрытии, даже если тесты упали.
  • needs позволяет деплою не ждать все задания, а только нужные.
  • rules ограничивает деплой веткой main.
  • environment + when: manual — прод только по кнопке.

Artifacts и cache — не одно и то же

ВопросArtifactsCache
Что этоРезультат job: отчёты, собранные файлыЗаготовки для ускорения: зависимости
Где хранитсяВ GitLabНа runner'е или в общем хранилище
Гарантировано лиДа, можно скачать и передать дальшеНет, может пропасть
Срок жизниЗадаётся expire_inПока не вытеснится
ЗачемПередать результат, сохранить отчётУскорить повторный запуск

Правило: если без файла pipeline сломается — это artifacts. Если файл нужен только для скорости — cache. Pipeline должен работать и с пустым кэшем.

Секреты — только в CI/CD variables. Не в .gitlab-ci.yml: этот файл лежит в репозитории. Переменные помечают masked (значение скрыто в логах) и protected (доступно только на защищённых ветках и тегах).

Деплой и откат

Деплой привязывается к окружению: environment: production. Тогда GitLab хранит историю выкладок, и откат — это повторный запуск pipeline с предыдущим тегом или коммитом. Для прода обычно включают protected environment: запускать деплой может только определённая роль.

6 Правила и частые ошибки

Шесть правил

  1. В main — только через MR. Прямой push выключен для всех.
  2. Merge только с зелёным pipeline и approvals. Оба условия обязательны.
  3. Новый коммит сбрасывает approvals. Иначе одобрят один код, а вольют другой.
  4. Секреты — в masked/protected variables. Не в YAML и не в логах.
  5. Деплой — с main или тега, прод — вручную. Никаких деплоев с любой ветки.
  6. Artifacts для результата, cache для скорости. Не наоборот.

Частые ошибки

  • Protected branch включён, но обязательный pipeline — нет. Merge проходит с падающими тестами.
  • Оставили прямой push для maintainer'ов — правила обходят «по-быстрому».
  • Автор может одобрить свой MR — approvals превращаются в галочку.
  • Секрет положили в .gitlab-ci.yml или залогировали через echo.
  • У качественного job стоит allow_failure: true — статический анализ никогда не блокирует merge.
  • Деплой-джоба без rules — прод обновляется с каждой ветки.
  • Кэш используют как хранилище результатов: на новом runner'е pipeline падает.
  • Огромные MR на тысячу строк — ревью формальное, ошибки проходят.
Если запомнить одно: GitLab защищает main не одной настройкой, а связкой «protected branch + обязательные approvals + зелёный pipeline». Убери любую часть — и защита превращается в декорацию.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Зачем нужен protected branch и что он запрещает?

«Protected branch запрещает прямой push и force-push в важную ветку, может требовать merge только через MR, обязательные approvals и успешный pipeline. Настраивается в Settings → Repository → Protected branches отдельно для main и шаблонов вроде release/*. Смысл — ни один разработчик, включая maintainer, не может обойти проверки».

Своими словами

Это дверь с охраной: напрямую в main не пройти, только через MR, с одобрением и зелёным pipeline.

02Что происходит с approvals после нового коммита?

«Если включена настройка сброса approvals при добавлении коммитов, все одобрения снимаются и собираются заново. Это защищает от ситуации, когда одобрили один код, а потом в тот же MR дослали другой. Force-push в MR обычно тоже сбрасывает approvals».

Своими словами

Изменил код — подписи сгорели, одобряем заново. Иначе после approval можно протащить что угодно.

03Чем artifacts отличаются от cache?

«Artifacts — результаты job, которые сохраняются в GitLab и передаются следующим стадиям или скачиваются; у них есть expire_in. Cache — ускоряет повторные запуски, хранится на runner'ах и не гарантирует наличие. Для корректности pipeline нужны artifacts, cache — только оптимизация».

Своими словами

Artifacts — коробка с результатом, её передают дальше. Cache — шкаф с заготовками, чтобы не делать всё заново. Если шкаф пропал, pipeline должен всё равно работать.

04Как устроен pipeline и что такое runner?

«Pipeline описывается в .gitlab-ci.yml: stages и jobs. Job — набор команд, stage — очередь. Jobs выполняются на runner'ах — агентах, зарегистрированных в проекте, группе или на уровне GitLab. Jobs внутри стадии идут параллельно, стадии — последовательно; needs позволяет запускать задание раньше, не дожидаясь всей стадии».

Своими словами

Конвейер: стадии по порядку, внутри каждой — задания. Задания выполняют runner'ы, то есть рабочие машины. needs позволяет не ждать всю стадию.

05Как сделать деплой только с main и с ручным подтверждением?

«В job деплоя ставлю rules с условием CI_COMMIT_BRANCH == "main", environment с именем production и when: manual. Дополнительно включаю protected environment, чтобы запускать мог только определённый круг ролей. Откат — повторный запуск pipeline с предыдущим тегом или коммитом».

Своими словами

Деплой-джоба запускается только на main и только после нажатия кнопки. Случайно в прод не улетит.

06Где хранить секреты в CI?

«В CI/CD variables, помеченных masked и protected: masked скрывает значение в логах, protected отдаёт переменную только на защищённых ветках и тегах. В .gitlab-ci.yml секретов быть не должно, файл лежит в репозитории. Для внешних систем лучше короткоживущие токены, а не долгоживущие пароли».

Своими словами

Секреты — в настройках GitLab, не в YAML. Маскирую, чтобы не светились в логах, и разрешаю только на защищённых ветках.
