Event-driven архитектура и Kafka

Чем событие отличается от команды, почему нельзя просто записать в БД и отправить в Kafka, как работает transactional outbox, версионирование событий, идемпотентный consumer и DLQ.

1 Событие vs команда

Команда — просьба что-то сделать: «опубликуй видео». Её можно отклонить. Событие — свершившийся факт: «видео опубликовано». Его не отменяют, на него реагируют.

Аналогия Команда — телефонный звонок: вы просите и ждёте ответа. Событие — газета: выходит факт, а кто и как его прочитает — дело подписчиков. Издатель не знает всех читателей.
ПодходСвязностьОтветСложность
Request-responseВысокая: знаем получателяСразуНизкая
СобытияНизкая: издатель не знает подписчиковАсинхронноДубли, порядок, отладка

Event-driven хорошо работает для интеграций и фоновых процессов: публикация видео, обновление поиска, уведомления, аналитика. Для «пользователь нажал — покажи результат» чаще проще прямой вызов.

Главная мысль. События снижают связность, но переносят сложность в доставку, порядок и согласованность. Это не бесплатный обмен.

2 Transactional outbox

Классическая ошибка — dual write: сначала записать в БД, потом отправить событие в Kafka. Между этими действиями нет атомарности. Если процесс упадёт после коммита, событие потеряется; если отправить до коммита — подписчики узнают о том, чего в БД нет.

Аналогия Вы записываете заказ в журнал и отдельно звоните на склад. Если телефон разрядился между действиями, журнал есть, а склад не знает. Outbox — это запись «позвонить на склад» в тот же журнал, откуда её точно заберут.

Как это работает

  1. В одной транзакции с бизнес-изменением пишем событие в таблицу `outbox`.
  2. Отдельный relay читает неотправленные записи и публикует их в Kafka.
  3. После успешной публикации помечает запись отправленной.
  4. При сбое relay повторит публикацию — доставка at-least-once.
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  aggregate_id bigint      NOT NULL,
  type         text        NOT NULL,
  payload      jsonb       NOT NULL,
  occurred_at  timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz
);

-- relay: забираем пачку, не мешая другим воркерам
SELECT *
FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

Relay может быть поллером или CDC-процессом (Debezium), который читает WAL. Поллер проще, CDC меньше нагружает приложение. В обоих случаях нужна идемпотентная обработка на стороне consumer'а: повтор возможен.

Порядок. События одного агрегата должны попадать в одну партицию: ключ — `aggregate_id`. Иначе «опубликовано» может прийти раньше «создано».

3 Контракты и версионирование событий

Событие — публичный контракт. Потребители могут быть разными командами и сервисами, поэтому менять схему «как получится» нельзя. Хороший конверт содержит метаданные и версию.

{
  "event_id": "c1f4e2a8-...",
  "type": "video.published",
  "version": 2,
  "occurred_at": "2026-03-01T10:15:22Z",
  "producer": "catalog",
  "aggregate_id": "42",
  "trace_id": "4f1c9a7b2e",
  "payload": {
    "video_id": 42,
    "title": "...",
    "published_at": "2026-03-01T10:15:22Z"
  }
}
СовместимостьЧто значит
BackwardНовые потребители читают старые события
ForwardСтарые потребители читают новые события, игнорируя неизвестные поля
FullИ то и другое

Правила эволюции

  • Добавляй только опциональные поля с значением по умолчанию.
  • Не переименовывай и не переиспользуй существующие поля.
  • Не меняй смысл поля молча — это ломает потребителей.
  • Крупное изменение — новый тип или мажорная версия.
  • Schema registry проверяет совместимость до публикации.
  • Contract-тесты ловят расхождение раньше прода.
Schema registry хранит схемы и проверяет совместимость (Avro, Protobuf, JSON Schema). Продюсер не сможет опубликовать несовместимое изменение, если режим совместимости задан.

4 Доставка, идемпотентность и DLQ

Kafka по умолчанию даёт at-least-once. Значит, consumer может получить одно событие дважды: после падения, ребаланса или повторной публикации. Это нормально, если обработка идемпотентна.

Идемпотентный consumer

  1. Проверить `event_id` в таблице обработанных.
  2. Если уже есть — пропустить, не выполняя бизнес-операцию.
  3. Если нет — выполнить операцию и записать `event_id` в одной транзакции.
  4. Закоммитить offset после успешной обработки.
INSERT INTO processed_events (event_id, processed_at)
VALUES ($1, now())
ON CONFLICT (event_id) DO NOTHING;

-- если вставлено 0 строк — событие уже обработано

Коммит offset после обработки даёт at-least-once. Коммит до обработки — at-most-once и риск потери. Exactly-once внутри Kafka возможен через транзакции, но внешние побочные эффекты всё равно требуют идемпотентности.

Ядовитое сообщение

Если событие стабильно ломает consumer, нельзя бесконечно повторять и блокировать партицию. Схема: несколько retry с задержкой → DLQ с причиной и исходным сообщением → алерт → ручной разбор. DLQ без разбора превращается в свалку.

Ребаланс. При добавлении consumer'а партиции перераспределяются. Обработка может приостановиться, а часть событий — прийти повторно. Consumer должен быть к этому готов, а offset коммититься только после завершения работы.

5 Kafka Streams и обработка потоков

Kafka Streams и ksqlDB позволяют считать агрегаты, соединять потоки и хранить состояние прямо в приложении. Состояние хранится в local state store и подкрепляется changelog-топиком.

  • Окна: «сколько просмотров за последние 5 минут».
  • Joins: обогатить событие данными каталога.
  • Агрегации: счётчики, топы, дедупликация по окну.
  • Exactly-once: транзакции внутри Kafka-пайплайна.

Но это отдельный runtime и новая сложность: состояние, ребалансы, changelog, мониторинг. Если задача — просто «на событие сходить в БД и отправить письмо», обычный consumer проще и надёжнее.

Event-driven ≠ Event Sourcing. Event-driven — обмен событиями между сервисами. Event Sourcing — хранение состояния как последовательности событий. Можно использовать первое без второго.

6 Эксплуатация

Топики и партиции

  • Один топик — один тип событий или близкое семейство.
  • Ключ определяет партицию и порядок; выбирай по агрегату.
  • Число партиций задаёт верхнюю границу параллелизма consumer'ов.
  • Retention — по времени или размеру; compaction — последнее значение по ключу.
  • ACL — кто может читать и писать; не давай всем всё.

Мониторинг

  • Consumer lag — главная метрика; рост означает, что не успеваем.
  • Размер DLQ и скорость разбора.
  • Ребалансы и время обработки.
  • Ошибки продюсера и задержка публикации outbox.
  • Свежесть данных в read-моделях.

Replay

Kafka позволяет перечитать события с начала или с offset. Это мощно для перестроения read-модели, но требует идемпотентных consumer'ов и понимания, что внешние побочные эффекты повторятся.

Kafka — не база данных. Она не заменяет произвольные запросы и хранение актуального состояния. События — журнал, состояние — в БД или read-модели.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Чем событие отличается от команды?

«Команда — просьба выполнить действие, её можно отклонить: „опубликуй видео“. Событие — свершившийся факт: „видео опубликовано“, его не отменяют. Команда обычно имеет одного адресата и ответ, событие — многих подписчиков и асинхронную реакцию».

Своими словами

Команда — звонок с просьбой, событие — новость о том, что уже случилось.

02Почему dual write ломается и как работает outbox?

«Запись в БД и публикация в Kafka — две разные системы, их нельзя закоммитить вместе. Если процесс упадёт между ними, данные и событие разойдутся. Outbox пишет событие в ту же транзакцию, что и бизнес-изменение, а отдельный relay публикует его после коммита. Доставка at-least-once, consumer идемпотентен».

Своими словами

Сначала кладём записку «отправить» в тот же ящик, что и заказ. Потом курьер её забирает. Ящик не теряет записку при падении.

03Как версионировать события?

«Добавляю только опциональные поля, не переименовываю и не меняю смысл существующих. Крупное изменение — новый тип или мажорная версия. Использую schema registry с режимом совместимости и contract-тесты. В конверте есть `event_id`, `type`, `version`, `occurred_at`, `producer`, `trace_id`».

Своими словами

Событие — публичный контракт. Расширять можно, ломать нельзя.

04Как сделать consumer идемпотентным?

«Храню `event_id` в таблице обработанных и проверяю перед бизнес- операцией. Запись `event_id` и изменение данных идут в одной транзакции. Offset коммичу после успешной обработки. Для побочных эффектов использую уникальные ключи или idempotency key».

Своими словами

Веду список уже обработанных номеров. Повторный номер просто пропускаю.

05Что делать с ядовитым сообщением?

«Не блокировать партицию бесконечными повторами. Несколько retry с задержкой, затем DLQ с причиной и исходным сообщением, алерт и ручной разбор. После исправления — повторная публикация из DLQ. DLQ нужно мониторить, иначе ошибки теряются».

Своими словами

Больное письмо откладываем в отдельный ящик, а не держим очередь из-за него.

06Когда нужны Kafka Streams, а когда обычный consumer?

«Streams — когда нужны окна, агрегаты, joins и состояние: метрики в реальном времени, обогащение, дедупликация. Обычный consumer — когда на событие нужно сходить в БД и выполнить действие. Streams добавляют runtime, state store и сложность эксплуатации, поэтому выбираю по задаче».

Своими словами

Если нужно просто «сделать действие по событию» — consumer. Если считать поток — Streams.

Ответь вслух, не подглядывая. 0 / 5

Если запомнить одно: событие — публичный контракт, outbox — атомарность, идемпотентность — защита от повторов, DLQ — место для того, что не удалось обработать.
