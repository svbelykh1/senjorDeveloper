1 Безопасность — это слои

Не существует одной кнопки «включить безопасность». Защита строится слоями: валидация входа, параметризованные запросы, экранирование вывода, права на сервере, безопасные заголовки, сканеры в CI. Если один слой пробит, следующий снижает ущерб.

Аналогия Замок, сигнализация и сейф. Каждый слой можно обойти отдельно, но вместе они делают кражу дорогой и заметной. Один замок на двери — не безопасность.

На интервью Senior не просят помнить все CVE. Проверяют модель угроз: какие данные защищаем, кто атакует, где границы доверия и какие меры реально применяются в коде.

Главная мысль. Безопасность — свойство системы, а не отдельного модуля. Она проверяется на входе, внутри и на выходе.

SQL-инъекция

Строка запроса собирается из пользовательского ввода, и `' OR 1=1 --` меняет смысл. Лечится параметризацией: запрос и данные идут отдельно.

// Плохо: конкатенация
$pdo->query("SELECT * FROM users WHERE email = '$email'");

// Хорошо: параметр
$stmt = $pdo->prepare('SELECT * FROM users WHERE email = ?');
$stmt->execute([$email]);

Дополнительно: минимальные права БД, никаких `DROP` для приложения, валидация типов и лимиты. ORM не отменяет правила, если использовать raw-запросы.

XSS

Чужой JavaScript попадает на страницу и крадёт токены или действия пользователя. Защита — контекстное экранирование вывода, CSP, `HttpOnly` cookie, отказ от `innerHTML` с пользовательскими данными.

CSRF

Браузер пользователя автоматически отправляет cookie на ваш сайт с чужой страницы. Защита: `SameSite=Lax/Strict`, CSRF-токен, проверка `Origin`, запрет менять состояние через `GET`.

Экранируй на выходе, а не только на входе. Один и тот же текст в HTML, атрибуте и JavaScript экранируется по-разному. Валидация входа не заменяет кодирование вывода.

3 Хеши, шифрование и пароли

ОперацияОбратимостьДля чего
Кодирование (base64)Обратимо без ключаПередача бинарных данных текстом
ШифрованиеОбратимо с ключомХранить данные, которые нужны обратно
ХешированиеНеобратимоПроверка целостности и паролей

SHA-256/512 — быстрые криптографические хеши. Они подходят для контрольных сумм, подписей и идентификаторов, но не для паролей: слишком быстрые, миллиарды вариантов перебираются железом.

// Пароль: медленный адаптивный хеш
$hash = password_hash($password, PASSWORD_ARGON2ID);
$ok   = password_verify($password, $hash);

// Целостность файла: быстрый SHA-256
$sum = hash_file('sha256', '/path/to/artifact');

Соль генерируется автоматически и хранится рядом с хешем. Перец (pepper) — дополнительный секрет приложения, хранится отдельно. Стоимость (cost/memory) настраивают так, чтобы проверка занимала десятки миллисекунд.

MD5 и SHA-1 для паролей — нет. Они быстрые и давно скомпрометированы. Не используй и самодельные схемы вроде «sha256(password + salt)» — только `password_hash` или Argon2id через проверенную библиотеку.

4 SAST, DAST и зависимости

ИнструментЧто анализируетКогдаМинус
SASTИсходный код без запускаНа MR, раноЛожные срабатывания
DASTРаботающее приложение снаружиStaging, nightlyНе видит код, медленнее
SCAЗависимости и их CVEНа каждый lock-файлШум от чужих библиотек
Secret scanningКлючи и токены в репозиторииPre-commit и CIНужно реагировать быстро

Порядок в CI: секреты и линтер → SAST → тесты → SCA → сборка → DAST на staging. Дешёвые проверки первыми. Критичные находки блокируют merge, остальные уходят в задачи с владельцем и сроком.

SAST не заменяет ревью. Он видит паттерны, но не бизнес-контекст. Ложные срабатывания подавляют точечно, с комментарием, а не отключением правила.

5 CORS: что это и чем не является

Браузер применяет same-origin policy: страница с одного origin не может читать ответ с другого без разрешения. CORS — механизм, которым сервер это разрешение выдаёт.

  • Простой запрос — `GET`, `POST` с обычным content-type.
  • Preflight — `OPTIONS` перед запросом с нестандартными заголовками или методами.
  • Access-Control-Allow-Origin — точный origin или `*`.
  • Credentials — с `*` несовместимы; нужен точный origin и `Allow-Credentials: true`.
  • Vary: Origin — чтобы прокси не смешивал ответы.
CORS — не авторизация. Он ограничивает браузер, но не защищает API от curl, мобильного клиента или чужого сервера. Токен и проверка прав нужны в любом случае. Отражать любой `Origin` с credentials — типичная уязвимость.

6 Практика: чек-лист безопасности

Заголовки

  • Content-Security-Policy — ограничить источники скриптов.
  • Strict-Transport-Security — только HTTPS.
  • X-Content-Type-Options: nosniff — не угадывать тип.
  • Referrer-Policy — не отдавать лишние URL.
  • frame-ancestors — защита от clickjacking.

Модель угроз на фичу

  1. Какие данные и операции защищаем.
  2. Кто может атаковать и какие у него возможности.
  3. Где границы доверия: браузер, gateway, сервис, БД.
  4. Какие входы недоверенные.
  5. Какие меры применяем и как проверяем.
// Пример безопасной проверки выхода по URL (SSRF)
$allowedHosts = ['cdn.example.com', 'drm.example.com'];
$host = parse_url($url, PHP_URL_HOST);

if (!in_array($host, $allowedHosts, true)) {
    throw new DomainException('host is not allowed');
}
Что показать на интервью. Назови три атаки и их защиту, объясни разницу SAST и DAST, скажи, почему SHA-256 не для паролей, и что CORS не заменяет авторизацию. Этого достаточно для уверенного уровня 3.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Как защититься от SQL-инъекции?

«Параметризованные запросы: SQL и данные передаются отдельно, драйвер экранирует значения. Плюс минимальные права БД, валидация типов и отказ от конкатенации пользовательского ввода. ORM помогает, но raw-запросы всё равно требуют параметров».

Своими словами

Не склеиваем команду и данные в одну строку. База должна получить их раздельно.

02Чем XSS отличается от CSRF?

«XSS — чужой JavaScript выполняется на вашей странице и действует от имени пользователя. CSRF — чужая страница заставляет браузер автоматически отправить запрос с cookie на ваш сайт. XSS лечится экранированием и CSP, CSRF — SameSite cookie, токеном и проверкой Origin».

Своими словами

XSS — враг пробрался в дом. CSRF — враг заставил вашего курьера отнести посылку по чужому адресу.

03Почему SHA-256 не подходит для паролей?

«Он слишком быстрый: на видеокартах перебираются миллиарды вариантов в секунду. Для паролей нужны адаптивные хеши с солью и настраиваемой стоимостью: Argon2id или bcrypt через `password_hash`. SHA-256 годится для целостности артефактов и подписей, но не для хранения паролей».

Своими словами

Замок должен открываться медленно. Быстрый хеш — это дверь без замка.

04Чем SAST отличается от DAST?

«SAST анализирует исходный код без запуска: рано, быстро, но бывают ложные срабатывания. DAST тестирует работающее приложение снаружи реальными запросами: видит конфигурацию и поведение, но не код и работает медленнее. Их дополняют SCA для зависимостей и сканирование секретов».

Своими словами

SAST читает чертёж, DAST стучится в готовый дом.

05Что такое CORS и почему он не заменяет авторизацию?

«CORS — механизм браузера, который разрешает или запрещает чтение ответа с другого origin. Он не защищает API от прямых запросов вне браузера. Авторизация должна проверяться на сервере по токену и правам. Опасная настройка — отражать любой Origin с credentials».

Своими словами

CORS — это правило для браузера, а не замок на API.

06Какие меры безопасности добавишь в пайплайн?

«Secret scanning и линтер на pre-commit, SAST на MR, SCA по lock-файлу, тесты, сборку, DAST на staging. Критичные находки блокируют merge, остальные — задачи с владельцем. Плюс заголовки безопасности, проверка прав на сервере и модель угроз на новую фичу».

Своими словами

Дешёвые проверки первыми, опасные — блокируют, остальные — в работу.
