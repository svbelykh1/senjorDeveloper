1 Зачем транзакции

Транзакция — это набор операций, который должен выполниться целиком или не выполниться вовсе. Списать деньги, записать платёж и активировать подписку нужно вместе: половина операции хуже, чем никакой.

Аналогия Перевод денег — это списание и зачисление. Если между ними пропадает связь, деньги не должны исчезнуть. Транзакция — это гарантия, что оба действия считаются одним.

ACID: атомарность, согласованность, изолированность, долговечность. На интервью Senior важно не прочитать расшифровку, а объяснить границы транзакции, уровень изоляции и что делать при конфликте.

Главная мысль. Транзакция должна быть короткой и охватывать только то, что действительно должно быть атомарным. Внешние вызовы внутри транзакции — почти всегда плохо.

Что это значит на практике

  • Грязное чтение — видим незакоммиченные данные другого транзакции. В норме не допускается.
  • Неповторяющееся чтение — прочитали строку, потом ещё раз, а значение изменилось.
  • Фантом — повторный запрос вернул новые строки.
  • Потерянное обновление — два писателя перезаписали друг друга. Лечится версией строки или блокировкой.
  • Write skew — два транзакции прочитали одно состояние и обе записали несовместимые изменения. Ловится Serializable или явной блокировкой.
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- ... операции ...

COMMIT;  -- при конфликте: ERROR 40001, повторить транзакцию
Serializable — не бесплатно. Он может прерывать транзакции с ошибкой сериализации. Приложение обязано повторить операцию. Без retry пользователь увидит случайную ошибку.

3 Транзакции и обработка ошибок

Правила

  • Короткая транзакция. Не держи открытой, пока идёт HTTP-вызов или отправка письма.
  • Единый порядок блокировок. Всегда обновляй строки в одном порядке, чтобы снизить риск дедлока.
  • Retry при дедлоке и serialization failure. С ограниченным числом попыток и backoff.
  • Обработка исключений. При ошибке — `ROLLBACK`; не оставляй соединение в незавершённой транзакции.
  • Идемпотентность. Повтор операции не должен создавать дубль.
  • Savepoint. Позволяет откатить часть работы, не всю транзакцию.
$pdo->beginTransaction();

try {
    $orders->reserve($orderId);
    $payments->charge($orderId);
    $pdo->commit();
} catch (Throwable $e) {
    $pdo->rollBack();
    throw $e;
}

Дедлок

Две транзакции держат разные строки и ждут друг друга. База выбирает жертву и откатывает её. Приложение должно повторить операцию. Помогает единый порядок обновления и короткие транзакции.

Не вызывай внешние сервисы внутри транзакции. Пока идёт вызов, блокировки держатся, пул занят, а откатить чужой платёж нельзя. Лучше outbox: записать намерение в БД и отправить после коммита.

4 Сложный SQL без страха

Читать план запроса

`EXPLAIN (ANALYZE, BUFFERS)` показывает, что реально делает Postgres: Seq Scan или Index Scan, сколько строк ожидалось и сколько получено, где узкое место. Без плана оптимизация — угадывание.

Полезные приёмы

  • Keyset-пагинация вместо `OFFSET` на больших таблицах.
  • Оконные функции для топ-N внутри группы.
  • CTE для читаемости, но проверяй план: в старых версиях CTE был барьером оптимизации.
  • `EXISTS` вместо `IN` с подзапросом, где возможны `NULL`.
  • Агрегаты заранее — материализованное поле или отдельная таблица, если считать на каждый запрос дорого.
-- Топ-3 видео по просмотрам за последние 7 дней
SELECT video_id, count(*) AS views
FROM video_views
WHERE created_at >= now() - interval '7 days'
GROUP BY video_id
ORDER BY views DESC
LIMIT 3;

-- Оконная функция: последний просмотр на пользователя
SELECT *
FROM (
  SELECT vv.*,
         row_number() OVER (
           PARTITION BY user_id
           ORDER BY created_at DESC
         ) AS rn
  FROM video_views vv
) t
WHERE rn = 1;

Keyset-пагинация: вместо `OFFSET 100000` используем `WHERE (created_at, id) < ($lastCreatedAt, $lastId) ORDER BY created_at DESC, id DESC LIMIT 20`. База не пересчитывает пропущенные строки.

N+1. Сто видео — сто запросов за авторами. Лечится `JOIN`, eager loading или одним запросом с `IN`. Это самая частая причина «медленно» в ORM-коде.

5 Хранимые процедуры

Когда полезны Массовая обработка рядом с данными, batch-миграции, сложные агрегаты, ограничение прямого доступа к таблицам через права.
Чем платим Логика размазывается между кодом и БД, сложнее тестировать и версионировать, привязка к конкретной СУБД, отладка хуже.

Для бизнес-логики обычно лучше держать правила в приложении, а в БД — операции, где важна близость к данным и атомарность. Триггеры применяют осторожно: они скрывают поведение и усложняют миграции.

Ответ для интервью. «Процедуры использую для тяжёлой пакетной обработки и миграций, где не хочу гонять данные по сети. Бизнес-правила держу в приложении: их проще тестировать и версионировать».

6 Практика: каталог и история просмотров

CREATE TABLE videos (
  id          bigserial PRIMARY KEY,
  title       text        NOT NULL,
  status      text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE video_views (
  id          bigserial,
  video_id    bigint      NOT NULL,
  user_id     bigint      NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE INDEX ON video_views (video_id, created_at DESC);
CREATE INDEX ON video_views (user_id, created_at DESC);
  • Партиционирование по дате — старые месяцы можно архивировать и удалять целиком.
  • Составной индекс `(video_id, created_at DESC)` — для топов и истории по видео.
  • EXPLAIN ANALYZE на медленном запросе — до и после индекса.
  • Эксперимент с изоляцией — воспроизвести lost update и показать, как его лечит версия строки.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Какие уровни изоляции знаешь и какие аномалии они допускают?

«Read Uncommitted допускает грязное чтение, но в Postgres фактически работает как Read Committed. Read Committed — дефолт: нет грязного чтения, но возможны неповторяющееся чтение и фантомы. Repeatable Read даёт снапшот, но возможен write skew. Serializable ловит и его, но может прерывать транзакции с ошибкой сериализации».

Своими словами

Чем строже уровень, тем меньше сюрпризов и больше конфликтов и цены.

02Что такое потерянное обновление и как его предотвратить?

«Два клиента прочитали одну версию строки и оба записали, второй затёр первый. Оптимистичная блокировка: поле `version`, `UPDATE ... WHERE version = ?`; если обновлено ноль строк — конфликт, повторяем. Альтернатива — `SELECT FOR UPDATE` или атомарный инкремент».

Своими словами

Двое правили один документ и сохранили поверх друг друга. Нужна проверка версии.

03Что делать при дедлоке?

«База откатывает одну транзакцию с ошибкой. Приложение ловит её и повторяет операцию с ограниченным числом попыток и backoff. Для профилактики — единый порядок блокировок, короткие транзакции и индексы, чтобы не блокировать лишние строки».

Своими словами

Двое застряли в дверях. Одного разворачивают, он заходит снова — но уже по правилам.

04Почему OFFSET плох для больших страниц?

«База всё равно пересчитывает и пропускает предыдущие строки, поэтому чем больше offset, тем дороже запрос. Keyset-пагинация использует условие по последнему ключу и индекс: `WHERE (created_at, id) < (...)`. Она стабильнее и быстрее, но не даёт прыгнуть на произвольную страницу».

Своими словами

OFFSET перелистывает все страницы заново. Keyset начинает с того места, где остановились.

05Как читать EXPLAIN ANALYZE?

«Смотрю узлы сверху вниз: тип сканирования, ожидаемое и фактическое число строк, время, loops и buffers. Большое расхождение ожидаемого и фактического говорит о плохой статистике. Seq Scan на большой таблице с фильтром — повод проверить индекс. Главное — найти узел, который даёт основное время».

Своими словами

Это отчёт о том, как база реально искала данные, а не как мы думали.

06Когда использовать хранимые процедуры?

«Для массовой обработки и миграций, где важно не гонять данные по сети и держать атомарность рядом с БД. Для бизнес-логики чаще выбираю приложение: её проще тестировать, версионировать и переносить. Триггеры — только когда без них нельзя обеспечить целостность».

Своими словами

Процедура хороша как тяжёлый станок на складе, а не как мозг всего бизнеса.
