1 Зачем контейнеры

Образ — это упакованное приложение со всеми зависимостями. Контейнер — запущенный экземпляр образа. Один и тот же образ работает на ноутбуке, в CI и в проде, потому что внутри зафиксированы версии библиотек и настройки.

Аналогия Образ — это чертёж и коробка с деталями. Контейнер — собранный по чертежу механизм. Можно собрать десять одинаковых механизмов из одной коробки, и они будут вести себя одинаково.

Kubernetes — оркестратор: он решает, где запустить контейнеры, перезапускает упавшие, распределяет трафик и масштабирует. На интервью Senior проверяют понимание иммутабельности, probes, requests/limits и стратегии релиза.

Главная мысль. Контейнер не «маленькая виртуалка», а процесс с изолированной файловой системой. Его нельзя лечить вручную — его заменяют новым экземпляром.

2 Docker: предсказуемый образ

Правила хорошего Dockerfile

  • Multi-stage. Сборка зависимостей отдельно от runtime-образа.
  • Кэш слоёв. Сначала копируем `composer.json` и ставим зависимости, потом код — так кэш не сбрасывается на каждое изменение.
  • Не root. Создаём пользователя и запускаем процесс от него.
  • Маленький базовый образ. Alpine или slim, без лишних пакетов.
  • .dockerignore. Не тащим `.git`, тесты и локальные артефакты.
  • Один процесс на контейнер. Логи — в stdout, состояние — наружу.
FROM composer:2 AS vendor
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --prefer-dist

FROM php:8.3-fpm-alpine
RUN adduser -D -u 1000 app
WORKDIR /app
COPY --from=vendor /app/vendor ./vendor
COPY . .
USER app
EXPOSE 9000
CMD ["php-fpm"]

Слои кэшируются: если не менялись `composer.json` и `composer.lock`, установка зависимостей не повторяется. Это ускоряет CI в разы.

Не храни секреты в образе. Переменные, токены и ключи передаются через окружение или секрет-хранилище. В слоях образа они остаются навсегда, даже если файл потом удалить.

4 Масштабирование и здоровье

Requests и limits

Requests — сколько ресурсов гарантировано pod'у; по ним планировщик выбирает узел. Limits — верхняя граница. Если памяти больше лимита, контейнер убивают (OOMKilled); если CPU — throttling.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"

Probes

  • Readiness — можно ли отправлять трафик. Провал убирает pod из Service.
  • Liveness — жив ли процесс. Провал перезапускает контейнер.
  • Startup — даёт время на медленный старт, не мешая liveness.

HPA

Horizontal Pod Autoscaler добавляет реплики по метрике: CPU, память, RPS или кастомной. Для PHP важнее метрика очереди или RPS, чем CPU: процесс может ждать БД, не нагружая процессор.

Не масштабируй stateful вслепую. Реплики с локальным диском или своим состоянием требуют StatefulSet, стабильных имён и аккуратной работы с данными. Stateless-сервис масштабируется горизонтально, stateful — по стратегии.

5 Релизы и откат

СтратегияКак работаетКогда
RollingUpdateПостепенно заменяет pod'ыОбычный релиз stateless-сервиса
RecreateСначала гасит все, потом поднимаетНесовместимые версии, простой допустим
Blue-greenДва окружения, переключение трафикаНужен мгновенный откат
CanaryМалая доля трафика на новую версиюРискованные изменения

Для RollingUpdate важны readinessProbe и graceful shutdown: новый pod не получает трафик, пока не готов, а старый дорабатывает текущие запросы. Без этого пользователь ловит 502 при релизе.

Откат. `kubectl rollout undo` возвращает предыдущую версию. Но если миграция БД несовместима, откат кода не поможет. Поэтому миграции делают обратно совместимыми: сначала добавить новое, потом переключить, потом удалить старое.

6 Практика: PHP-сервис в Kubernetes

  1. Собрать образ. Multi-stage Dockerfile, non-root, логи в stdout.
  2. Описать Deployment. Реплики, requests/limits, readiness и liveness, graceful shutdown.
  3. Открыть Service. ClusterIP внутри, Ingress снаружи.
  4. Вынести конфиг. ConfigMap для настроек, Secret для паролей.
  5. Добавить HPA. По RPS или длине очереди, а не только CPU.
  6. Проверить отказ. Убить pod, отключить узел, посмотреть, что трафик не теряется.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: playback
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
  template:
    spec:
      containers:
        - name: app
          image: registry/playback:1.4.2
          readinessProbe:
            httpGet: { path: /health/ready, port: 8080 }
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }
          resources:
            requests: { cpu: "250m", memory: "256Mi" }
            limits:   { cpu: "1",    memory: "512Mi" }
Что проверить перед релизом: образ собран из тега, а не `latest`; миграции совместимы; readiness отвечает; PDB не даёт убить всё сразу; HPA видит метрику; алерты на ошибки и задержку включены.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01Чем образ отличается от контейнера?

«Образ — неизменяемый шаблон с приложением и зависимостями. Контейнер — запущенный экземпляр образа со своим процессом и файловой системой. Из одного образа можно запустить много контейнеров, и они будут одинаковыми. Контейнер не лечат, а заменяют».

Своими словами

Образ — чертёж, контейнер — собранная по нему машина.

02Зачем multi-stage сборка и кэш слоёв?

«Multi-stage отделяет сборку зависимостей от runtime: в финальный образ не попадают компиляторы и dev-пакеты. Кэш слоёв ускоряет сборку: если `composer.json` не менялся, зависимости не переустанавливаются. Вместе это даёт меньший и быстрее собираемый образ».

Своими словами

Собираем в мастерской, а в рейс берём только готовую машину без инструментов.

03Чем readiness отличается от liveness?

«Readiness говорит, готов ли pod принимать трафик: провал убирает его из Service. Liveness проверяет, жив ли процесс: провал перезапускает контейнер. Если перепутать, можно получить бесконечные рестарты или трафик в неготовый инстанс. Startup probe даёт время на медленный старт».

Своими словами

Readiness — «можно входить», liveness — «я ещё жив».

04Что такое requests и limits?

«Requests — гарантированные ресурсы, по ним планировщик выбирает узел. Limits — максимум. Превышение памяти приводит к OOMKilled, превышение CPU — к throttling. Если requests завышены, pod не разместится; если занижены, начнёт деградировать под нагрузкой».

Своими словами

Requests — забронированное место, limits — потолок, выше которого не пустят.

05Как масштабируется stateless-сервис и что делать со stateful?

«Stateless масштабируется горизонтально: HPA добавляет pod'ы, Service распределяет трафик, состояние вынесено в Redis или БД. Stateful требует StatefulSet, стабильных имён, PersistentVolume и стратегии репликации. Его не масштабируют вслепую: сначала продумывают данные и консистентность».

Своими словами

Сервис без памяти можно плодить сколько угодно. С памятью — сначала решаем, где она живёт.

06Как безопасно выкатить новую версию?

«RollingUpdate с readiness и graceful shutdown, обратно совместимые миграции, PDB, метрики и алерт. Для рискованных изменений — canary или blue-green. Откат — `rollout undo`, но он не отменяет миграцию, поэтому схема должна быть совместима с обеими версиями».

Своими словами

Меняем по одному, проверяем здоровье и держим кнопку отката.

Ответь вслух, не подглядывая. 0 / 5
