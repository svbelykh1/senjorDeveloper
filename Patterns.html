Паттерны, ООП vs ФП, DI и feature toggles

1 Зачем нужны паттерны

Паттерн — это название для повторяющегося решения. Как «дверная ручка» в разговоре с плотником: не нужно объяснять устройство, все понимают, о чём речь. Паттерны нужны для общего языка и для быстрого узнавания знакомой конструкции, а не как обязательный список к применению.

Аналогия Кулинарный рецепт — не приказ готовить только так. Это проверенная последовательность действий, которую можно адаптировать. Если рецепт не подходит к продуктам, его меняют, а не ломают ужин.

На интервью Senior обычно спрашивают не «перечисли 23 паттерна GoF», а: какой паттерн ты применял и почему, что он дал и чем пришлось заплатить. Ответ «использую Strategy, чтобы менять тарификацию без правки checkout» звучит сильнее, чем заученный список.

Паттерн ради паттерна — антипаттерн. Если задача решается в пять строк без абстракций, паттерн добавит файлов и слоёв, но не пользы. Абстракция должна окупаться: её вводят, когда есть второе реальное применение или ожидаемая замена.

2 ООП vs ФП: где что уместно

ООП собирает состояние и поведение вместе: у объекта есть данные и методы, которые с ними работают. ФП строит программу из функций: данные передаются снаружи, функции по возможности чистые, результат — новое значение, а не изменённый объект.

ООП сильнее, когда… Есть предметная область с множеством сущностей и правил: заказ, подписка, видео. Нужен полиморфизм: разные реализации за одним интерфейсом. Состояние живёт долго и должно быть инкапсулировано.
ФП сильнее, когда… Есть преобразования данных: списки, отчёты, DTO, валидация. Нужна предсказуемость и лёгкое тестирование. Операции можно разложить на маленькие шаги и собирать из них конвейер.

Пять терминов простыми словами

ТерминЧто значитПример в PHP
Чистая функция Одинаковый вход даёт одинаковый выход, побочных эффектов нет `function vat(int $sum): int { return intdiv($sum * 20, 120); }`
Иммутабельность Объект не меняется, вместо изменения возвращается новый `readonly`-свойства, методы `withStatus()`
Функция высшего порядка Принимает или возвращает функцию `array_map`, `array_filter`, `usort` с callback
Композиция Собираем сложное поведение из простых функций `compose(trim(...), strtolower(...))`
Мемоизация Кэшируем результат функции по аргументам Кэш тарифов по `userId` на время запроса 
$normalize = fn (string $s): string => mb_strtolower(trim($s));

$emails = array_map($normalize, $rawEmails);

$unique = array_values(array_unique($emails));

В PHP оба подхода живут вместе. Сервисы и сущности удобно держать в ООП, а преобразования внутри — в виде чистых функций. Плохой признак — когда объект одновременно хранит состояние, ходит в базу, шлёт письма и форматирует ответ: это уже не ООП, а «божественный объект».

Ответ для интервью. «Выбираю по задаче: ООП — для предметной области и полиморфизма, ФП — для преобразований и тестируемых расчётов. В PHP они не конкурируют: сервис может быть объектом, а его внутренние шаги — чистыми функциями».

3 Паттерны GoF: что реально нужно

«Банда четырёх» описала 23 паттерна и разделила их на три группы. Запоминать все не нужно. Достаточно уверенно знать шесть-восемь и уметь объяснить, какую проблему каждый решает.

ГруппаПаттерныОбщая идея
ПорождающиеFactory Method, Abstract Factory, Builder, SingletonКак создавать объекты, не размазывая `new` по коду
СтруктурныеAdapter, Decorator, Facade, Proxy, CompositeКак собрать объекты в удобную конструкцию
ПоведенческиеStrategy, Observer, Command, Template Method, Chain of Responsibility, StateКак распределить поведение и связи между объектами

Strategy — подменяемая логика

Когда есть несколько вариантов одного действия: тарификация, ретраи, выбор транскодера. Вместо `if/else` по типу — общий интерфейс и разные реализации.

interface PricingStrategy
{
    public function price(Order $order): int;
}

final class RegularPricing implements PricingStrategy { /* ... */ }
final class PromoPricing implements PricingStrategy   { /* ... */ }

final class Checkout
{
    public function __construct(private PricingStrategy $pricing) {}

    public function total(Order $order): int
    {
        return $this->pricing->price($order);
    }
}

Adapter — мост к чужому API

Внешний клиент CDN имеет неудобный интерфейс. Adapter переводит его в наш: остальной код не знает, чья библиотека под капотом, и её можно заменить.

interface Cdn
{
    public function purge(string $path): void;
}

final class CloudCdnAdapter implements Cdn
{
    public function __construct(private CloudClient $client) {}

    public function purge(string $path): void
    {
        $this->client->invalidate(['paths' => [$path]]);
    }
}

Decorator — добавить поведение, не меняя класс

Логирование, кэш, метрики, проверка прав — всё это можно навесить слоями вокруг исходного объекта. Каждый слой реализует тот же интерфейс.

final class LoggingVideoRepository implements VideoRepository
{
    public function __construct(
        private VideoRepository $inner,
        private LoggerInterface $log,
    ) {}

    public function find(int $id): ?Video
    {
        $this->log->info('video.find', ['id' => $id]);

        return $this->inner->find($id);
    }
}

Остальные — коротко

  • Factory Method — создать объект по типу: `hls` → `HlsTranscoder`, `dash` → `DashTranscoder`. `new` живёт в одном месте.
  • Observer — событие домена рассылается подписчикам: «видео опубликовано» → обновить поиск, отправить уведомление, прогреть CDN.
  • Facade — простой интерфейс к сложной подсистеме: один метод `publishVideo()` вместо десяти вызовов.
  • Proxy — тот же интерфейс, но с дополнительным контролем: ленивая загрузка, права, кэш.
  • Chain of Responsibility — обработчики по цепочке: валидация → обогащение → сохранение. Каждый решает, передать дальше или остановить.
  • Template Method — базовый класс задаёт скелет процесса, наследники переопределяют шаги: импорт каталога с разными источниками.
Singleton — осторожно. Он удобен для «одного на всё приложение», но часто превращается в глобальную переменную: скрытые зависимости и проблемы в тестах. Если нужен один экземпляр — обычно лучше доверить это DI-контейнеру.

4 IoC и DI: кто кого создаёт

Инверсия управления (IoC) — класс больше не создаёт свои зависимости сам, а получает их снаружи. Внедрение зависимостей (DI) — самый распространённый способ это сделать: передать готовый объект в конструктор.

Плохо: зависимость создаётся внутри `new RedisClient(...)` прямо в сервисе. Нельзя подменить в тесте, конфигурация размазана, связанность жёсткая.
Хорошо: зависимость приходит снаружи Конструктор принимает интерфейс. В проде — Redis, в тесте — fake. Класс не знает, откуда взялся объект. 
interface Cache
{
    public function get(string $key): ?string;
    public function set(string $key, string $value, int $ttl): void;
}

final class VideoService
{
    public function __construct(private Cache $cache) {}

    public function preview(int $id): ?string
    {
        return $this->cache->get("video:{$id}");
    }
}

Контейнер

DI-контейнер — это фабрика, которая знает, как собрать объект: какой класс подставить под интерфейс, какие у него зависимости, создавать один раз или каждый раз новый. В Laravel это service providers, в Symfony — `services.yaml` с autowire.

// Laravel: интерфейс → реализация
$this->app->bind(Cache::class, RedisCache::class);

// Symfony: services.yaml
// App\Service\VideoService:
//     arguments:
//         $cache: '@App\Cache\RedisCache'

Чем DI лучше Service Locator

Service Locator — класс сам достаёт зависимости из глобального контейнера: `app(Cache::class)`. Зависимости спрятаны внутри, по конструктору не видно, что нужно классу. В тестах приходится поднимать весь контейнер, а замена одной зависимости может неожиданно сломать другую.

// Service Locator: зависимость скрыта
final class Report
{
    public function send(): void
    {
        $mailer = app(Mailer::class); // откуда? кто знает...
        $mailer->send('...');
    }
}

DI делает зависимости явными: всё видно в конструкторе, тест подставляет fake, порядок создания контролирует контейнер. Это и есть главный ответ на интервью: DI — про явность и тестируемость, а не про «модно».

Не усложняй. В маленьком скрипте контейнер не нужен: хватит конструктора и явной передачи. DI окупается, когда граф зависимостей растёт и появляются интерфейсы с несколькими реализациями.

5 Feature toggles: включать без деплоя

Feature toggle — переключатель, который включает или выключает поведение без нового релиза. Это страховка: код уже в проде, но новая функция доступна не всем или выключена до готовности.

ТипЗачемСколько живёт
Release toggleСлить код раньше, включить позжеДни или недели
Experiment toggleA/B-тест: часть пользователей видит новоеДо конца эксперимента
Ops toggle / kill switchБыстро отключить тяжёлую функцию при инцидентеДолго, сознательно
Permission toggleДоступ по тарифу или ролиДолго, это часть продукта
 
if ($this->flags->isEnabled('new_player', $user)) {
    return $this->newPlayer->handle($request);
}

return $this->oldPlayer->handle($request);

Как не превратить toggle в вечный `if`

  1. У каждого переключателя есть владелец и дата удаления. Записывай их рядом с флагом или в задаче.
  2. Release toggle удаляют после раскатки. Код новой ветки становится основным, старый удаляется. Иначе через год никто не помнит, зачем `if`.
  3. Не вкладывай toggle в toggle. Два-три уровня условий — и поведение уже невозможно проверить.
  4. Тестируй оба состояния. Выключенная ветка — тоже продакшен-код. Хотя бы smoke-тест на оба пути.
  5. Логируй вариант. Без этого нельзя разобрать инцидент: у кого именно было включено.
  6. Не используй toggle как конфиг. Постоянные настройки — это конфигурация, а не фича-флаг.
Признак запущенности: в коде есть флаг трёхлетней давности, все всегда включён, а рядом лежит мёртвая ветка. Это уже не гибкость, а технический долг.

6 Баланс переиспользования и сложности

Переиспользование звучит как добро, но у него есть цена: связность. Общая библиотека связывает все проекты, которые её используют. Изменение в одном месте ломает три других, и появляются флаги совместимости.

Когда абстракция окупается Есть два-три реальных потребителя. Правило стабильно и повторяется. Замена реализации ожидается в обозримом будущем.
Когда вредит Абстракция «на будущее», которого нет. Один потребитель и пять интерфейсов. Слой ради слоя, через который трудно пройти отладчиком.

Три правила, которые спасают

  • Правило трёх. Первый раз — пиши просто. Второй — терпи дублирование. Третий — выделяй общее. До третьего случая ещё неизвестно, что именно общее.
  • YAGNI. «You aren't gonna need it»: не строь механизм под гипотетическое требование. Требование изменится раньше, чем механизм пригодится.
  • Композиция вместо наследования. Наследование жёстко связывает классы и плохо переносит изменение иерархии. Композиция собирает поведение из независимых частей.

На интервью это проверяют вопросом «когда абстракция вредит?». Хороший ответ: «когда она введена до появления второго потребителя и добавляет слой, который не окупается. Тогда проще дублировать, пока не станет понятно, что именно обобщать».

Главная мысль. Паттерн, DI, toggle и переиспользование — инструменты, а не цели. Хорошая архитектура делает изменение дешёвым, а не максимально «правильным» на бумаге.

7 Вопросы и самопроверка

У каждого вопроса два ответа: модельный — структура и формулировки для интервью, и «своими словами» — как это звучит вживую.

01ООП или ФП: где что уместно в PHP-микросервисе?

«ООП — для предметной области, сущностей и полиморфизма: заказ, подписка, разные реализации за интерфейсом. ФП — для преобразований данных, расчётов и валидации: чистые функции, `array_map`, композиция. В PHP они сочетаются: сервис — объект, его шаги внутри — чистые функции. Главный критерий — где меньше скрытого состояния и проще тестировать».

Своими словами

ООП — про «кто» и «что умеет», ФП — про «как преобразовать данные». Смешивать их нормально, лишь бы объект не превращался в комбайн.

02Чем DI отличается от Service Locator и почему второго избегают?

«DI передаёт зависимости явно, обычно через конструктор: по сигнатуре видно, что нужно классу. Service Locator достаёт их из глобального контейнера внутри метода: зависимости скрыты, тест требует весь контейнер, замена одной может сломать другую. DI лучше тестируется и честнее описывает связи».

Своими словами

DI — «мне принесли инструменты», Service Locator — «я сам пошёл в кладовку». Во втором случае никто не знает, что мне понадобится.

03Какие паттерны GoF ты используешь и зачем?

«Strategy — когда несколько вариантов одного действия, например тарификация или выбор транскодера. Adapter — чтобы изолировать чужой API за своим интерфейсом. Decorator — для логирования, кэша и метрик без правки основного класса. Observer — для доменных событий. Factory — чтобы `new` жил в одном месте. Остальные применяю по необходимости, а не для коллекции».

Своими словами

Паттерн — это ответ на конкретную боль: много вариантов, чужой API, сквозная логика, событие. Если боли нет, паттерн не нужен.

04Как не превратить feature toggle в вечный `if`?

«У флага есть владелец и дата удаления. Release toggle удаляется сразу после раскатки: новая ветка становится основной, старая вычищается. Не вкладываю флаги друг в друга, тестирую оба состояния и логирую вариант. Постоянные настройки держу в конфиге, а не в фича-флаге».

Своими словами

Флаг — это временные леса, а не часть здания. Когда ремонт закончен, леса убирают, иначе они мешают жить.

05Когда абстракция вредит?

«Когда введена до появления второго реального потребителя и добавляет слой, который не окупается. Тогда изменение становится дороже: нужно пройти через интерфейс, фабрику и конфиг, чтобы поменять одну строку. До третьего случая дублирование дешевле, потому что ещё неизвестно, что именно общее».

Своими словами

Абстракция — это кредит: сначала удобно, потом платишь связностью. Брать его стоит, когда есть понятная выгода.

06Наследование или композиция?

«По умолчанию композиция: класс собирает поведение из независимых частей, и замена одной части не ломает иерархию. Наследование уместно, когда есть настоящая связь «является» и общий контракт с шаблонными шагами. Но глубокая иерархия быстро становится хрупкой: изменение базового класса задевает всех наследников».

Своими словами

Композиция — «у меня есть двигатель», наследование — «я и есть двигатель». Первое легче заменить.

Ответь вслух, не подглядывая. 0 / 5

Если запомнить одно: паттерны и абстракции — это кредит под будущие изменения. Бери его, когда выгода видна, и возвращай вовремя: удаляй флаги, упрощай лишние слои.
